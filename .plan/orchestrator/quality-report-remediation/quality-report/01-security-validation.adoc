.Severity decisions
* *F-A-1 (High, confirmed by the lead).* `%25%32%66` passes every preset and the pipeline returns `%2f`; `%25%30%30` returns `%00`. The record component `allowDoubleEncoding=false` and requirement HTTP-9 promise that double encoding is blocked. The value returned to the caller still carries a complete encoding layer, so a consumer that decodes once more sees `/` or NUL. Traversal-shaped payloads are still caught by later stages, which is why this is High and not Critical.
* *F-A-2 (High, confirmed by the lead).* The decoded-delimiter rule for parameter names runs before Unicode normalisation; U+037E (a canonical NFC singleton) folds to `;` afterwards, so the parameter-name pipeline returns `a;b`, which is exactly the output the rule exists to prevent. The lead's probe additionally shows `/a%EF%BC%9Bb` → `/a;b` and `/a%C2%A0b` → `/a b` for the path pipeline without `UNICODE_NORMALIZATION_CHANGED`.
* *F-A-3 (proposed High, recorded Medium).* The case-sensitive prefix match is wrong against the RFC 6265bis text the class cites and against browsers, and the test suite pins the wrong behaviour. It is recorded as Medium because the failure direction is "validator accepts a cookie the browser will reject": no server-side trust decision in this library is based on the prefix, so the consequence is an availability defect and a false compliance claim rather than a bypass. It should still be fixed.
* *L-1 / F-A-8 (Medium).* The clamp is RFC-conformant for the *returned* value, and ADR-0014 documents clamping. The defect is that no document tells integrators they must use the returned value, that the ADR's scoping statement ("only a `..` sequence long enough to walk past root") is not what the pipeline does (`/a/b/..` walks up one level and is accepted), and that a trailing slash flips the verdict.
* *F-B-1, F-B-2, L-3 (Medium).* Together they describe the content-type pipeline: list entries are not normalised the way values are (a copied `text/html; charset=utf-8` entry blocks nothing), a `null` Content-Type bypasses an allow-list, and the pipeline has no length or character stage, so `application/json; x\r\nX: y` passes an allow-list of `application/json`.
* Everything else is recorded at the severity the stream proposed.

.What was verified as correct
The three "Verified strengths" sections below list roughly sixty specific checks that passed: every encoded traversal spelling in the attack databases, the `..;` path-parameter family, overlong sequences that are on the regex list, NFKC structural-fold detection, CR/LF rejection in header types under every preset, exactly-once event counting, thread safety of shared pipelines, and the stage orders documented in five places.

== Lead reviewer findings (`+L-+`)

These items come from the lead reviewer's own read of the security core and three compiled probe programs run against `+cui-http-core/target/classes+` built from HEAD (6 993 tests green). Items that a stream later reported in more depth are marked as such; the stream item is the primary record.

=== L-1 Segment-terminal `+..+` (no trailing separator) is not treated as traversal; pipeline accepts and rewrites
* Severity: Medium | Category: false-security | CONFIRMED (probe)
* URLPathValidationPipeline default/strict/lenient/paranoid (paranoid confirmed by the adversarial verification): `+/a/b/..+` -> ACCEPT `+/a+`; `+/files/public/..+` -> ACCEPT `+/files+`; `+/..+` -> `+/+`; `+/a/%2e%2e+` -> `+/+`; `+/%2e%2e+` -> `+/+`; `+/%2F%2F..+` -> `+/+`; `+/./././..+` -> `+/+`. Meanwhile `+/a/b/../+` (trailing slash) is REJECTED (PATH_TRAVERSAL_DETECTED). Only difference: trailing slash.
* Root cause: SecurityDefaults.PATH_TRAVERSAL_PATTERNS entries all require a following separator ("../", "..\\", "..%2F"...); PatternMatchingStage ENCODED_TRAVERSAL_PATTERN/DOT_SEPARATOR_PATTERN likewise; NormalizationStage LAYER 1 patterns (SINGLE_COMPONENT_TRAVERSAL_PATTERN requires a trailing segment; CONTAINS_* need separators) so a terminal `+..+` reaches RFC 3986 resolution and is consumed (NormalizationStage.processPathSegment ".." branch).
* ADR-0014 claims the clamp "applies only to the residual case ... a `+..+` sequence long enough to walk past root". `+/a/b/..+` does not walk past root: it walks up ONE directory and is accepted. So the ADR's scoping statement is inaccurate and the canonical example `+/api/../../etc/passwd+` never reaches the clamp through any factory pipeline (PatternMatchingStage pass 1 rejects `+../+`).
* Risk: a caller that validates the wire path and then forwards the ORIGINAL string (common integration pattern, nowhere forbidden in docs) forwards a one-level upward traversal (`+/files/public/..+` -> backend resolves `+/files+`). Safe only if caller uses the returned normalized value; no doc states "you MUST use the returned value".
* Recommendation: treat a `+..+` path segment anywhere (including terminal) as traversal intent in PatternMatchingStage/NormalizationStage LAYER 1, or document the contract "consumers MUST use the returned value" prominently in README/security-readme/pipeline Javadoc; fix ADR-0014 scoping text.

=== L-2 Malformed (non-overlong) UTF-8 percent sequences are silently accepted as U+FFFD; Javadoc claims INVALID_ENCODING
* Severity: Medium | Category: correctness / documentation | CONFIRMED (probe)
* DecodingStage Javadoc: "INVALID_ENCODING - if URL decoding fails due to malformed input", "Blocks malformed UTF-8 encoding attacks". URLDecoder.decode(..., UTF_8) never throws on malformed byte sequences; it substitutes U+FFFD.
* Probe (URL_PATH default): `+/a/%80+` -> `+/a/�+`; `+/a/%c3+` -> `+�+`; `+/a/%f5%80%80%80+` -> 4x U+FFFD; `+/a/%f4%90%80%80+` (> U+10FFFF) accepted; `+/a/%ed%a0%80+` (encoded UTF-16 surrogate) accepted; `+/a/%c0%80+` (2-byte overlong NUL, "modified UTF-8") accepted as U+FFFD U+FFFD — NOT caught by UTF8_OVERLONG_PATTERN because `+%c0%[a-f][0-9a-f]+` needs second nibble a-f and `+%c[0-1][0-9a-f]+` needs a literal hex char after %c0; `+%f0%8f%bf%bf+` (4-byte overlong) accepted.
* Not a traversal bypass (replacement char is inert), but the "fail closed on invalid encoding" claim is only true for the regex blocklist. Canonicalization mismatch risk with downstream Latin-1 decoders (%ff -> 'ÿ' vs U+FFFD here).
* Recommendation: decode with a CharsetDecoder configured with CodingErrorAction.REPORT and map MalformedInputException to INVALID_ENCODING; or document "malformed UTF-8 is replaced, not rejected" and drop the regex.

=== L-3 ContentTypeValidationPipeline enforces nothing beyond list membership; CRLF and unbounded length pass
* Severity: Medium | Category: false-security | CONFIRMED (probe)
* ContentTypeValidationPipeline.createStages = List.of(AllowBlockListStage.forContentTypes(config)) only — no LengthValidationStage, no CharacterValidationStage.
* Probe: default config (empty lists): `+text/html\r\nX-Injected: 1+` ACCEPTED; `+"a"*5000+` ACCEPTED; `+totally not a media type+` ACCEPTED. With allowedContentTypes={application/json}: `+application/json; x\r\nX: y+` ACCEPTED (only media type before ';' compared); `+application/json;+` + 100000 chars ACCEPTED.
* The pipeline reports ValidationType.HEADER_VALUE, so a caller may assume header-value character rules apply. They do not.
* Recommendation: prepend LengthValidationStage + CharacterValidationStage(HEADER_VALUE) in ContentTypeValidationPipeline; document that with empty lists the pipeline is a no-op.

=== L-4 AllowBlockListStage embeds the raw value (incl. CR/LF) in the exception detail -> log forging
* Severity: Medium | Category: security-gap / consistency | CONFIRMED (probe)
* AllowBlockListStage.validate: detail("Value '" + value + "' is block-listed") / "... not in the allow-list". Every other stage escapes control chars (CharacterValidationStage.handleInvalidCharacter, DecodingStage.escaped, HttpHandler.sanitizeForMessage). UrlSecurityException.getMessage() sanitizes the `+(input: ...)+` suffix but NOT the detail.
* Probe: message = `+... Invalid input - Value 'x/y\r\nInjected: yes' is not in the allow-list (input: 'x/y??Injected: yes')+` — raw CR LF inside the message.
* Recommendation: do not echo the value in detail (originalInput already carries it), or apply the same escaping.

=== L-5 CookiePrefixValidationStage.validateCookie validates prefix rules only; cookie name/value content is not validated, and prefix match is case-sensitive
* Severity: Medium | Category: false-security | CONFIRMED (probe)
* Probe (validateCookie): name `+a\r\nb+`, `+a b+`, `+a;b+`, `+a=b+` ACCEPTED; value `+v\r\nSet-Cookie: x+` ACCEPTED; `+__host-a+` and `+__HOST-a+` without Secure ACCEPTED; `+__secure-a+` without Secure ACCEPTED. `+validate(String)+` (name-only) accepts `+a\r\nb+` too (only trims whitespace).
* PipelineFactory.createPipeline(COOKIE_NAME/COOKIE_VALUE) throws "not yet implemented", so there is NO cookie content pipeline; CharacterValidationStage(COOKIE_*) exists but is only wired into Cookie.hostPrefix()/securePrefix() factory suffix checks (Cookie.java COOKIE_NAME_VALIDATOR).
* RFC 6265bis (draft-ietf-httpbis-rfc6265bis, since -10) specifies case-insensitive prefix matching ("case-insensitive match for the string __Secure-"); browsers (Chromium) implement this. SUSPECTED for the exact draft number; CONFIRMED that code is case-sensitive.
* Recommendation: either wire LengthValidationStage + CharacterValidationStage(COOKIE_NAME/COOKIE_VALUE) into validateCookie or rename/document the stage as prefix-only; make prefix detection case-insensitive.

=== L-6 Cookie attribute lookup is first-wins; RFC 6265 §5.3 is last-wins
* Severity: Low | Category: correctness | CONFIRMED (probe)
* `+new Cookie("n","v","Secure; Path=/; Path=/x").getPath()+` -> `+/+`; `+Domain=a; domain=b+` -> `+a+`. RFC 6265 §5.3 steps 7-9: "the last attribute-value wins". Consequences: `+__Host-a; Secure; Path=/; Path=/x+` passes validateCookie although a browser sets Path=/x and rejects the __Host- cookie; `+Secure; Path=/x; Path=/+` is rejected although a browser accepts it.
* Location: AttributeParser.extractAttributeValue (first match returned).

=== L-7 RequestCollectionValidator counts distinct parameter names, not parameter instances
* Severity: Low | Category: false-security | CONFIRMED (probe)
* validateParameters(Map<String,?>) -> parameters.size(). A `+Map<String, List<String>>+` with 1 key x 10000 values is ACCEPTED under maxParameterCount=100. Repeated parameters (`+?a=1&a=2&...+`) — the classic parameter-flood DoS — are not bounded. configuration.adoc:230 shows `+validator.validateParameters(request.getParameterMap())+` (String[] values) as the usage.
* Recommendation: count values when the map values are Collection/array, or document the limitation.

=== L-8 PARAMETER_VALUE character set is narrower than RFC 3986 query grammar; raw `+/+`, `+:+`, `+@+` rejected
* Severity: Medium | Category: correctness / consistency | CONFIRMED (probe)
* CharacterValidationConstants.RFC3986_QUERY_CHARS Javadoc: "RFC 3986 query characters". RFC 3986 §3.4: query = *( pchar / "/" / "?" ), pchar includes ":" and "@". The set omits "/", ":", "@".
* Probe (PARAMETER_VALUE default): `+/home+` REJECT INVALID_CHARACTER; `+http://x+` REJECT; `+a@b.com+` REJECT; `+10:30+` REJECT; while `+a%2Fb+` -> `+a/b+` and `+a%3Ab+` -> `+a:b+` ACCEPT. Browsers do not percent-encode `+/ : @+` in link query strings (`+?next=/home+`, `+?url=https://...+`), so legitimate wire values are rejected as INVALID_CHARACTER; conversely the traversal tests for parameter values only exercise PATH_TRAVERSAL_DETECTED through encoded forms (`+../+` raw is rejected as INVALID_CHARACTER for the `+/+`).
* Also: no document tells integrators to pass the still-encoded wire value rather than the container-decoded `+request.getParameter()+` value (which the pipeline would decode a second time and whose raw `+/+` it would reject).
* Recommendation: either align the set with RFC 3986 (add / : @) and rely on PatternMatchingStage for traversal, or rename the constant/Javadoc to state the deliberate narrowing; add an integration note "feed wire-form (still percent-encoded) values".

=== L-9 Decoded Unicode format/invisible characters are accepted in URL paths
* Severity: Low | Category: security-gap | CONFIRMED (probe)
* DecodingStage.validateDecodedCharacters rejects NUL, combining marks (Mn/Mc/Me) and Cc controls, citing homograph risk. It does not reject Cf (format) or Zs/Zl/Zp: `+/a/%e2%80%ae+` (U+202E RLO) -> ACCEPT; `+/a/%e2%80%8b+` (ZWSP) -> ACCEPT; `+/a/%ef%bb%bf+` (BOM) -> ACCEPT; `+/a/%c2%a0+` (NBSP) -> ACCEPT. Same homograph/visual-spoofing class the combining-mark rule exists for; C1 controls via `+%c2%85+` ARE rejected.
* Recommendation: extend the decoded-character rule to Character.FORMAT (and optionally LINE/PARAGRAPH_SEPARATOR) or document the boundary.

=== L-10 LENIENT preset: single decode leaves dangerous encoded sequences in the returned value
* Severity: Low | Category: documentation | CONFIRMED (probe)
* lenient: `+/a/%2500+` -> ACCEPT `+/a/%00+` (allowDoubleEncoding=true; decoded once). A consumer that decodes again gets NUL. Not wrong per se (lenient is opt-in) but configuration.adoc should state the returned value may still carry percent-encoded bytes under allowDoubleEncoding.

=== L-11 Duplicated default literals between SecurityConfigurationBuilder and SecurityDefaults
* Severity: Low | Category: duplication | CONFIRMED (code)
* SecurityConfigurationBuilder fields: maxPathLength=4096, maxParameterNameLength=128, maxParameterValueLength=2048, maxHeaderNameLength=128, maxHeaderValueLength=2048, maxCookieNameLength=128, maxCookieValueLength=2048, maxBodySize=5MB as literals; SecurityDefaults has MAX_*_DEFAULT constants with the same values but the builder only references the *_COUNT_* constants. Builder validation (`+<= 0+`) duplicates the record compact-constructor validation. Drift risk.

=== L-12 ADR-0007 / trust manager: null socket also drops TLS-layer algorithm constraints and stapled OCSP, not only hostname verification
* Severity: Low | Category: documentation | SUSPECTED at the time of writing; since CONFIRMED against JDK sources by stream C, see F-client-2 in xref:03-http-client.adoc[] (superseded) (JDK source not available offline; based on JDK 21 sun.security.ssl.X509TrustManagerImpl.checkTrusted)
* With a null Socket/SSLEngine the JDK path is `+v.validate(chain, null, Collections.emptyList(), null /*constraints*/, authType)+`: (a) no SSLAlgorithmConstraints derived from the handshake (jdk.tls.disabledAlgorithms / peer-signature constraints) are applied — only the certpath-level jdk.certpath.disabledAlgorithms remain; (b) stapled OCSP responses from the session are not passed to the validator. ADR-0007 states "chain trust, expiry, and algorithm constraint enforcement continue to run unchanged" — over-claims for the TLS-layer constraints.
* Recommendation: soften the ADR/Javadoc wording; verification by a JDK-source reader recommended.

=== L-13 ADR-0014 canonical example is unreachable through factory pipelines
* Severity: Info | Category: documentation | CONFIRMED (probe)
* `+/api/../../etc/passwd+` is rejected by PatternMatchingStage pass 1 (`+../+`) in every factory pipeline; NormalizationStage alone clamps it to `+/etc/passwd+`. The ADR describes stage-level behaviour as if it were pipeline behaviour. The case that actually reaches the clamp via the pipeline is L-1 (terminal `+..+`).

== Item added by the adversarial verification (`+V-+`)

=== V-1 A decoded `+?+`, `+#+` or invisible character glued to a `+..+` segment passes every preset and the returned value still carries the dot-dot
* Severity: Medium | Category: false-security / correctness | CONFIRMED (executed by the adversarial verifier, `+P6Missed.java+`; see xref:07-adversarial-verification.adoc[])
* URLPathValidationPipeline, defaults and strict: `+/files/public/..%3F+` -> ACCEPT `+/files/public/..?+`; `+/a/b/..%23/c+` -> ACCEPT `+/a/b/..#/c+`; `+/a/b/%2e%2e%3f%2fetc%2fpasswd+` -> ACCEPT `+/a/b/..?/etc/passwd+` (paranoid rejects this one only because of the `+/etc/+` block-list entry); `+/a/b/%2e%2e%c2%a0/c+` -> ACCEPT `+/a/b/.. /c+` (NBSP); `+/a/b/..%e2%80%8b/c+` -> ACCEPT `+/a/b/..\u200B/c+` (ZWSP).
* Root cause: `+PatternMatchingStage+` needs a separator after `+..+`; `+NormalizationStage+` compares whole segments, and `+..?+` is not `+..+`; `+DecodingStage.validateDecodedCharacters+` treats a decoded `+?+`/`+#+` as an ordinary character for `+URL_PATH+` (only combining marks, controls and NUL are re-checked, and the structural-fold check applies to Unicode normalisation only).
* Why it matters: unlike L-1, the pipeline's *own output* contains the `+..+`. A consumer that re-parses the returned string as a URL sees the path `+/files/public/..+` (`+URI.create("https://h" + out).getPath()+`), which normalises to `+/files/+`. So the mitigation for L-1 ("consumers must use the returned value") does not close this variant. The `+?+`/`+#+` terminates the path on re-parse, so at most one level is walked; this is not a root escape.
* Recommendation: reject a decoded `+?+` and `+#+` for `+URL_PATH+` in `+DecodingStage.validateDecodedCharacters+` (they can only have been percent-encoded on the wire and become structural once decoded), and treat any segment that *starts with* `+..+` as traversal intent in `+PatternMatchingStage+`/`+NormalizationStage+` LAYER 1 (which also fixes L-1/F-A-8). Add regression tests for the five inputs above.

=== Findings

==== F-A-1: Double-encoding gate is bypassed by percent-encoding the hex digits (`+%25%32%66+` → output `+%2f+`, `+%25%30%30+` → output `+%00+`)
* Severity: High
* Category: security-gap / false-security
* Status: CONFIRMED (executed)
* Location: `+DecodingStage.java:117+` (`+DOUBLE_ENCODING_PATTERN = "%25[0-9a-fA-F]{2}"+`), `+:178-185+` (only check), `+:201+` (single `+URLDecoder.decode+`), no re-check of the decoded output for a remaining `+%XX+` layer.
* Evidence (probe output, `+SecurityConfiguration.defaults()+` *and* `+strict()+`):
----
  DecodingStage/PATH | in=/a%252fb      -> REJECT DOUBLE_ENCODING
  DecodingStage/PATH | in=/a%25%32%66b  -> PASS out=/a%2fb
  DecodingStage/PATH | in=/a%252%66b    -> PASS out=/a%2fb
  PathPipeline/def   | in=/a%25%32%66b  -> PASS out=/a%2fb
  PathPipeline/def   | in=/api/%25%30%30 -> PASS out=/api/%00
  PathPipeline/strict| in=/a%25%32%66b  -> PASS out=/a%2fb
  ParamValuePipeline/def | in=a%25%32%66b -> PASS out=a%2fb
----
* Analysis: The gate only recognises the *literal spelling* `+%25+` + two hex digits in the wire form. Encoding one or both hex digits (`+%25%32%66+`, `+%252%66+`) defeats it, and after the single decode the pipeline *returns a value that still carries a complete second encoding layer* (`+%2f+`, `+%00+`). Every downstream consumer that decodes once more (a servlet container mapping the returned path, `+URI+`, `+URLDecoder+`, a reverse proxy) sees `+/+` or NUL. This is exactly the class HTTP-9 ("The system must detect and block double-encoded input", `+doc/http-security/functional-requirements.adoc:129-131+`) and the record component `+allowDoubleEncoding+` promise to close. Traversal-shaped payloads happen to be caught later (`+/api/%25%32%65%25%32%65/x+` is rejected by `+NormalizationStage+`'s `+%2e%2e+` intent check, and `+..%2f+` by the post-pattern pass), so this is not a traversal bypass, but arbitrary bytes (`+%00+`, `+%2f+`, `+%3b+`, `+%5c+`, …) reach the caller undecoded while the configuration says double encoding is blocked. No test in the tree exercises this shape (`+MixedEncodingAttackTest.java:126+` uses `+%25%32%65%25%32%65%25%32%66+`, which is rejected for traversal reasons, not for double encoding).
* Recommendation: Decide double encoding on the *decoded* output, not on the wire spelling: after `+decodeForValidationType+`, if `+!config.allowDoubleEncoding()+` and the decoded string still contains `+%+` followed by two hex digits (or simply any `+%+` that was produced by decoding `+%25+`), throw `+DOUBLE_ENCODING+`. Keep the wire-form regex only as a fast path. Add tests for `+%25%32%66+`, `+%252%66+`, `+%25%30%30+` in `+DecodingStageTest+` and in `+DoubleEncodingAttackTest+`.

==== F-A-3: Cookie prefix matching is case-sensitive; RFC 6265bis and every major browser match `+__Host-+`/`+__Secure-+` case-insensitively, so `+__host-…+` bypasses every prefix rule; `+__Http-+`/`+__HostHttp-+` are not implemented
* Severity: Medium (reviewer proposed High; adjusted, see consolidation notes)
* Category: false-security
* Status: CONFIRMED (executed + spec)
* Location: `+CookiePrefixValidationStage.java:236+` (`+cookieName.startsWith(HOST_PREFIX)+`), `+:242+`, `+:321-344+` (helpers), Javadoc `+:106+` ("Case-Sensitive — Cookie name prefixes are case-sensitive per RFC"), `+:104+` ("Implements RFC 6265bis prefix requirements"). Test that pins the wrong behaviour: `+CookiePrefixValidationStageTest.java:269-274+` (`+"__host-session", "__HOST-session"+` asserted as *no* prefix).
* Evidence:
----
  cookie __Host-s   attrs=Path=/ -> REJECT COOKIE_PREFIX_VIOLATION __Host- prefix requires Secure attribute
  cookie __host-s   attrs=Path=/ -> PASS
  cookie __HOST-s   attrs=Path=/ -> PASS
  cookie __secure-s attrs=Path=/ -> PASS
  cookie __Http-s   attrs=Path=/ -> PASS
  cookie __HostHttp-s attrs=Path=/ -> PASS
----
* Analysis: draft-ietf-httpbis-rfc6265bis (the document the class cites in `+@see+`) states for both prefixes "If a cookie's name begins with a *case-insensitive* match for the string `+__Secure-+`/`+__Host-+` …", and Chromium/Firefox implement the check case-insensitively (this is precisely one of the PortSwigger "Cookie Chaos" bypasses the class claims to prevent, `+:110-118+`). ==== F-A-4: Malformed / uncovered overlong UTF-8 percent sequences are silently decoded to U+FFFD and returned — never `+INVALID_ENCODING+`
* Severity: Medium
* Category: correctness / false-security
* Status: CONFIRMED (executed)
* Location: `+DecodingStage.java:125-133+` (`+UTF8_OVERLONG_PATTERN+`), `+:188-195+`, `+:270+` (`+URLDecoder.decode(.., UTF_8)+` replaces malformed bytes, never throws), Javadoc `+:61, 158-161+` ("INVALID_ENCODING – if URL decoding fails due to malformed input", "Blocks malformed UTF-8 encoding attacks").
* Evidence:
----
  PathPipeline/def | in=/a%c0%80b            -> PASS out=/a��b     (overlong NUL)
  PathPipeline/def | in=/a%c0%8ab            -> PASS out=/a��b     (overlong LF)
  PathPipeline/def | in=/a%ffb               -> PASS out=/a�b
  PathPipeline/def | in=/a%80b               -> PASS out=/a�b
  PathPipeline/def | in=/a%ed%a0%80b         -> PASS out=/a�b           (UTF-8-encoded surrogate)
  PathPipeline/def | in=/a%f8%80%80%80%afb   -> PASS out=/a�...b        (5-byte overlong '/')

----
* Analysis: The first regex alternative `+%c[0-1][0-9a-f]+` (`+:127+`) is malformed — it matches `+%c0+` followed by a *bare* hex digit (`+/a%c0ab+` is rejected) but not `+%c0%8X+`, so the overlong encodings of all C0 controls (`+%c0%80+`–`+%c0%9f+`) escape the "always blocked – security critical" check. ==== F-A-8: `+NormalizationStage+` traversal-intent and clamp rules are internally inconsistent and not "RFC 3986 §5.2.4 exactly"
* Severity: Medium
* Category: correctness / false-security
* Status: CONFIRMED (executed)
* Location: `+NormalizationStage.java:203+` (`+SINGLE_COMPONENT_TRAVERSAL_PATTERN+`), `+:419-429+` (root clamp), `+:430-433+` (empty segments dropped), `+:605-609+` (`+escapesRoot+` only for relative paths), Javadoc `+:157-164+` and ADR-0014 l.48 ("implements RFC 3986 Section 5.2.4 exactly").
* Evidence (standalone stage, `+defaults()+`):
----
  a/../b            -> REJECT PATH_TRAVERSAL_DETECTED        /a/../b   -> PASS out=/b
  a/../b/c          -> PASS out=b/c                          /../../etc/passwd -> PASS out=/etc/passwd
  /a/b/../../../c   -> PASS out=/c                           api/..    -> PASS out=""      .  -> PASS out=""
  /a//b///c/        -> PASS out=/a/b/c/                      //evil.com/x -> PASS out=/evil.com/x
  PathPipeline/def: /api/..  -> PASS out=/     /api/%2e%2e -> PASS out=/     /a/b/%2e%2e -> PASS out=/a
----
* Analysis: (1) The LAYER-1 "intent" rule fires only for the exact shape `+seg/../seg+` with no leading slash; adding a leading slash or a third segment turns the same intent into an accepted, silently rewritten path. That is a fingerprint, not a rule, and it is what the class Javadoc example `+api/../admin+` advertises. (2) `+DIRECTORY_ESCAPE_ATTEMPT+` is unreachable for absolute paths (the clamp swallows every root-consumed `+..+`), so for servlet-style request paths — always absolute — the failure type documented at `+:286+` can never occur. (3) RFC 3986 §5.2.4 does *not* drop empty segments; `+/a//b+` → `+/a/b+` and `+//evil.com/x+` → `+/evil.com/x+` are rewrites beyond the RFC (the latter changes a protocol-relative reference into a path — protective if the caller uses the output, misleading if the caller uses the original after "validation passed"). (4) `+"."+` and `+"api/.."+` normalise to the empty string. (5) Inside the full path pipeline the pre-decode `+PatternMatchingStage+` rejects every `+../+` unconditionally, so the only `+..+` forms that reach this stage are trailing `+/..+`, `+/%2e%2e+`, `+/.%2e+` — and those are *resolved and accepted* (`+/api/%2e%2e+` → `+/+`) while `+/api/%2e%2e/+` is rejected. A caller cannot predict which spelling is rejected and which is rewritten.
* Recommendation: Pick one contract and apply it uniformly: either (a) reject any `+..+` segment for `+URL_PATH+` (the pattern stage already does this for all but the trailing form — add `+(^|/)\.\.$+` there), making the clamp dead code, or (b) drop `+SINGLE_COMPONENT_TRAVERSAL_PATTERN+` and document that this stage resolves and clamps. Preserve empty segments (or document the deviation and stop claiming "exactly"). Have `+escapesRoot+` also flag an absolute path whose `+..+` count exceeded depth if that is meant to be an error.

==== F-B-4: Parameter pipelines reject raw RFC 3986 query characters (`+/ : @+`) that browsers send unencoded, yet accept the identical percent-encoded spellings — false positives with no security value
* Severity: Medium
* Category: correctness (false-security on the "RFC 3986 query characters" claim)
* Status: CONFIRMED (jshell)
* Location: src/main/java/de/cuioss/http/security/validation/CharacterValidationConstants.java:177-185 (`+RFC3986_QUERY_CHARS+` = unreserved + `+?&=!$'()*+,;+` — omits `+/ : @+` which RFC 3986 §3.4 `+query = *( pchar / "/" / "?" )+` permits); composed by src/main/java/de/cuioss/http/security/pipeline/URLParameterValidationPipeline.java:37 ("Validates RFC 3986 query characters") and :118, URLParameterNameValidationPipeline.java:102; DecodingStage.java:359-410 (`+validateDecodedCharacters+` does not re-check set membership)
