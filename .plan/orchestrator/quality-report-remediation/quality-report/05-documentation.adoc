== Consolidation notes

This document is review stream F (`F-documentation-`), covering every AsciiDoc and Markdown file, all 14 `package-info.java` files and the class-level Javadoc of every public type. Documentation defects that were found by the code-area streams are cross-referenced rather than repeated:

* F-documentation-2 = F-client-6 (and part of F-B-12): the non-compiling, security-inverted "Security Integration" samples.
* F-documentation-3, -16 = parts of F-B-12: Javadoc examples with wrong constructors or whole query strings fed to the value pipeline.
* F-documentation-4 = F-client-5 + F-D-9: the false log-coverage claim; this document carries the complete identifier table, which shows the catalogue itself is exact.
* F-documentation-5 = F-D-8; F-documentation-7 = F-E-8; F-documentation-8 overlaps F-E-1 and F-E-8; F-documentation-10 = F-B-11.
* Severity adjustments: F-documentation-1 was proposed as High, recorded as Medium in consolidation and as Low after the adversarial verification (the README does document the Maven wrapper for humans). F-documentation-2 is recorded as Medium and F-documentation-3 as Low, both on the verifier's reasoning that a non-compiling sample is caught at first copy. The `.plan/` directory does exist in the clone (with `marshal.json` and `project-architecture/`), and `.gitignore` documents that the executor is runtime tooling "managed by plan-marshall", so the situation is intentional. The defect that remains is that the four documents forbid the working fallback (`./mvnw`) without saying what to do when the executor is absent, which is exactly the situation in this review environment.
* The most consequential documentation findings for a *user* of the library are F-documentation-2, -8, -10, -14, -15 and -16: each of them describes a protection or a usage that the code does not deliver.
* The "Verified strengths" list is long on purpose: configuration tables, stage orders, TLS and redirect claims, every link and anchor, and every class name mentioned in the documentation were checked and are correct.

== Findings

=== F-documentation-1: Canonical build command in CLAUDE.md / agents.md / README / testing.adoc points at a script that is not in the repository
* Severity: Low (reviewer proposed High; adjusted to Medium in consolidation and to Low after adversarial verification, see consolidation notes)
* Category: documentation
* Status: CONFIRMED
* Location: CLAUDE.md:20-27; agents.md:10,18-21,42-44,127-129; README.adoc:132-133; doc/http-security/specification/testing.adoc:262-271
* Evidence: CLAUDE.md:20 `+Never hard-code build tool commands (./mvnw, mvn) — invoke builds via the canonical executor commands below:+` … `+python3 .plan/execute-script.py plan-marshall:build-maven:maven run --command-args "compile"+`. Shell: `+ls .plan/execute-script.py+` → `+No such file or directory+`; `+.plan/+` itself exists (it carries `+marshal.json+` and `+project-architecture/+`), but `+execute-script.py+` does not. `+.gitignore:16-21+` ignores `+.plan/*+` and whitelists only `+marshal.json+`, `+project-architecture/+`, `+plugin-doctor.yml+`, `+project-structure.json+` — `+execute-script.py+` is not whitelisted.
* Analysis: Every build/test/quality-gate instruction the project gives to agents (and the README's note to agents) depends on a tool that a fresh clone does not contain and that Git will never carry. CLAUDE.md and agents.md simultaneously forbid the working fallback (`+./mvnw+`, which does exist); README.adoc:126-129 does document `+./mvnw+` for human contributors (correction after adversarial verification), but the agent instructions that reference the executor do not. An agent following the docs literally cannot run the mandatory pre-commit gate. `+.plan/temp/+` (CLAUDE.md:156, agents.md:153) is likewise a directory that does not exist.
* Recommendation: Either commit the executor (or a bootstrap that fetches it) and whitelist it in `+.gitignore+`, or document `+./mvnw …+` as the fallback when `+.plan/execute-script.py+` is absent. Say explicitly that `+.plan/+` is created by external tooling.

=== F-documentation-2: "Security Integration" code samples in `+client+` and `+client.adapter+` package-info do not compile and give security-wrong guidance
* Severity: Medium (reviewer proposed High; adjusted after adversarial verification — a non-compiling sample is caught at first copy; the inverted-contract point is what remains)
* Category: false-security / documentation
* Status: CONFIRMED
* Location: cui-http-core/src/main/java/de/cuioss/http/client/package-info.java:296-317; cui-http-core/src/main/java/de/cuioss/http/client/adapter/package-info.java:226-330, 358-435 (line numbers corrected after adversarial verification; F-client-6 in xref:03-http-client.adoc[] cites the same locations)
* Evidence (client/package-info):
----
  HTTPHeaderValidationPipeline headerValidator = new HTTPHeaderValidationPipeline();
  headerValidator.validate(headerName).orElseThrow(() -> new UrlSecurityException("Header injection detected"));
  URLParameterValidationPipeline paramValidator = new URLParameterValidationPipeline();
  paramValidator.validate(paramValue).orElseThrow(() -> new UrlSecurityException("XSS attack detected"));
----
  adapter/package-info additionally: `+import de.cuioss.http.security.UrlSecurityException;+` (line 464), `+URLParameterValidationPipeline bodyValidator = new URLParameterValidationPipeline(); … bodyValidator.validate(jsonBody)+` (486-490), "This prevents SQL injection, XSS scripts, path traversal, and malicious Unicode" (483), checklist "All request bodies validated with URLParameterValidationPipeline" (583).
  Code: `+HTTPHeaderValidationPipeline+` has exactly one constructor `+(SecurityConfiguration, SecurityEventCounter, ValidationType)+` (HTTPHeaderValidationPipeline.java:105); `+URLParameterValidationPipeline+` only `+(SecurityConfiguration, SecurityEventCounter)+` (URLParameterValidationPipeline.java:99); `+UrlSecurityException+` has a single `+private+` constructor (UrlSecurityException.java:106) and lives in `+de.cuioss.http.security.exceptions+`; `+validate()+` returns `+Optional.empty()+` only for `+null+` input and throws on violations (HttpSecurityValidator.java:107-126).
* Analysis: Four independent compile errors (no-arg constructors ×2, String constructor, wrong package). Semantically the `+.orElseThrow(...)+` branch can only fire for a `+null+` input, so the "XSS attack detected"/"Header injection detected" messages describe something that never happens; real violations propagate as the pipeline's own exception. The body-validation advice contradicts functional-requirements.adoc HTTP-1 ("Body validation is not provided"), specification.adoc:318-324 (XSS/SQL signature detection deliberately removed) and compliance-traceability.adoc §Limitations; and because `+PARAMETER_VALUE+` uses `+RFC3986_QUERY_CHARS+` (CharacterValidationConstants.java:122-133: unreserved + `+? & = ! $ ' ( ) * + , ;+`), any JSON body containing `+"+`, `+{+`, `+}+` or a space is rejected as `+INVALID_CHARACTER+` — a caller who follows the checklist either gets 100% rejection or, if they drop it, believes they had SQL/XSS protection that never existed.
* Recommendation: Rewrite both sections using `+PipelineFactory.createHeaderValuePipeline(config, counter)+` / `+createUrlParameterPipeline(...)+`, catch `+UrlSecurityException+` instead of `+orElseThrow+`, delete the "request body validation" subsection and checklist item (or point to the HTTP-1 statement that bodies are an application-layer concern), and fix the import.

=== F-documentation-8: http1-vulnerabilities-analysis attributes detections to `+CharacterValidationStage+` that it does not perform
* Severity: Medium
* Category: false-security
* Status: CONFIRMED
* Location: doc/http-security/analysis/http1-vulnerabilities-analysis.adoc:63, 152, 347
* Evidence: ":63 CharacterValidationStage - Detects CRLF injection patterns (`+%0d%0a+`)"; ":152 CharacterValidationStage - Detects embedded HTTP verbs and CRLF patterns". Code: CharacterValidationStage.java:167-170 — for `+HEADER_NAME+`/`+HEADER_VALUE+` `+allowPercentEncoding = false+`, so `+%+` is checked as a plain character (`+RFC7230_HEADER_CHARS+` = 32–126, which contains `+%+`, `+0+`, `+d+`, `+a+`); the stage rejects only raw CR/LF for header types (lines 341-343). `+grep -n "GET\|POST\|verb" CharacterValidationStage.java+` → nothing but a comment about rendering. The header pipeline has no `+DecodingStage+` (HTTPHeaderValidationPipeline.java:141-146), so `+%0d%0a+` in a header value passes the header pipeline unchanged.
* Analysis: A reader of the analysis doc will believe percent-encoded CRLF in header values is caught. * Recommendation: Reword to "rejects raw CR/LF and other control characters; percent-encoded CRLF is only decoded and rejected in the path/parameter pipelines, never in the header pipeline"; delete the "embedded HTTP verbs" claim.
