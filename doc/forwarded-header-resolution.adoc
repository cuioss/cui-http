== Overview

The `de.cuioss.http.forwarded` package resolves the family of reverse-proxy / forwarded HTTP
headers into a single, normalized, *sanitized*, immutable structure. It folds the three otherwise
duplicated concerns of forwarded-header handling into one component:

. *Reconciliation* of an overlapping set of headers (proprietary + de-facto + standard), each
  resolved independently and compared rather than ranked.
. *Normalization* (context-path slashes, host/port splitting, canonical client IP).
. *Injection hardening + sanitization* (CR/LF and control characters, protocol-relative `//host`,
  backslashes) — reusing the existing xref:security-readme.adoc[security validation pipelines]
  rather than hand-rolling guards.

It is *transport-agnostic* (it consumes a `Function<String, List<String>>` header accessor, so no
servlet/Jetty type leaks in) and *secure-by-default* (nothing is honored unless a deployment opts
in explicitly).

[WARNING]
.Security precondition — the request must have arrived through a trusted proxy (MANDATORY)
====
*Prefer `resolve(Function<String, List<String>>, InetAddress peer)`.* Given the socket remote
address, this overload checks the peer in code: forwarded headers are honored only when the peer is
itself a configured trusted proxy, and a request from any other peer resolves to
`ResolvedForwarding.empty()` whatever its headers claim. A trusted peer is permission to *read* the
headers, not to believe them uncritically — the chain walk and every guard below still apply.

The header-only overload `resolve(Function<String, List<String>>)` *trusts HTTP headers, not the
socket.* It receives only a header accessor, so the `X-Forwarded-For` / `Forwarded` walk cannot
verify that a request actually arrived *through* a trusted proxy — it can only match the addresses
*inside the headers* against the configured `trustedProxies`. A deployment that uses it *MUST*
guarantee that only trusted proxies can connect to this server directly; otherwise an attacker can
forge the chain (e.g. a single untrusted entry `X-Forwarded-For: 6.6.6.6`) and have it returned
verbatim as the client IP.

Either way, network controls — bind the listener to a private interface, restrict it with
firewall / security-group rules, or place it behind a service mesh — remain worth having as defence
in depth. With the peer-checking overload they are no longer the only thing standing between a
direct connection and a forged chain.

*The header accessor MUST expose every instance of a repeated header, in wire order.* A proxy
appends by adding a repeated header line just as legitimately as by extending a comma-separated
value, so a single-valued accessor built on `request.getHeader(name)` exposes only the *first*
instance and hides the nearest hop's contribution — leaving the resolver looking at the attacker's
forged value. Pass `name \-> Collections.list(request.getHeaders(name))`, or the equivalent
all-instances accessor for your transport.
====

=== The header family

[cols="2,1,3", options="header"]
|===
| Header(s) | Status | Resolved into

| `X-Forwarded-Proto` / `-Host` / `-Port`
| de-facto convention (no RFC)
| scheme / host / port

| `X-Forwarded-Prefix`
| de-facto (Spring Cloud Gateway, Traefik, …)
| context-path prefix

| `X-Forwarded-For`
| de-facto convention (no RFC)
| client IP (via the trusted-proxy walk)

| `Forwarded` (RFC 7239)
| the only IETF-standard header — but it has *no* prefix/context-path directive
| scheme (`proto`), host (`host`), client IP (`for`)

| `X-ProxyScheme` / `-Host` / `-Port` / `-ContextPath`
| Apache NiFi-proprietary
| scheme / host / port / context-path prefix
|===

Because the one standardized header (RFC 7239 `Forwarded`) cannot express a path prefix, the
prefix is resolved only from the proprietary/de-facto headers.

== Components

=== xref:../cui-http-core/src/main/java/de/cuioss/http/forwarded/ForwardedHeaderResolver.java[ForwardedHeaderResolver]

The entry point. Immutable and thread-safe. Constructed with a
xref:../cui-http-core/src/main/java/de/cuioss/http/forwarded/ForwardedResolverConfig.java[ForwardedResolverConfig]
and a `SecurityEventCounter`; it internally builds a header-value sanitization pipeline via
`PipelineFactory.createHeaderValuePipeline(...)`.

[source,java]
----
ResolvedForwarding resolve(Function<String, List<String>> headerLookup, InetAddress peer) // preferred
ResolvedForwarding resolve(Function<String, List<String>> headerLookup)
----

The two-argument overload returns `ResolvedForwarding.empty()` unless `peer` falls within
`trustedProxies`, and otherwise delegates to the one-argument form — see the security precondition
above. The `Function<String, List<String>>` header accessor is the only header input, so the resolver works with
Jetty `Request`, `jakarta.servlet.HttpServletRequest`, or a plain `Map<String, List<String>>` in
tests — without leaking any transport type. The accessor maps a header name to *every* instance of
that header present on the request, in wire order; `null` or an empty list means the header is
absent.

That multi-instance shape is a *security* requirement, not a convenience: the repeated instances are
joined in wire order before nearest-hop token selection runs, so an accessor that returns only the
first instance — anything built on `request.getHeader(name)` — hides the appended, proxy-attested
value and resolves the attacker's forged one instead.

[source,java]
----
// Servlet
resolver.resolve(name -> Collections.list(request.getHeaders(name)));

// Tests
Map<String, List<String>> headers = Map.of("X-Forwarded-Proto", List.of("https", "http"));
resolver.resolve(headers::get);
----

For each field the resolver:

. resolves each source family *independently* — the two de-facto families are reconciled against
  each other first, then the result is reconciled against RFC 7239 `Forwarded` (see
  xref:#header-precedence[Header precedence]; only the context path uses an ordered first-present
  lookup),
. *sanitizes* each value through the header-value pipeline (see
  xref:#_sanitization_and_injection_guards[Sanitization and injection guards] for what it rejects),
. applies field-specific *normalization* and injection guards, and
. *honors* it only when the configured trust model permits.

A value that fails sanitization is dropped and logged (`HTTP-122`). A value that is merely *not
trusted* is also dropped, but only the context-path drop is logged, and at `DEBUG`; scheme, host,
port, and client IP are discarded without a log line.

`resolve` is fail-safe for request-time use in the sense that no rejected header value produces an
exception — but it is not exception-free. It throws `NullPointerException` for a `null`
`headerLookup`, propagates any `RuntimeException` thrown by the caller-supplied lookup, and
propagates any non-`UrlSecurityException` escaping the sanitization pipeline.

=== xref:../cui-http-core/src/main/java/de/cuioss/http/forwarded/ResolvedForwarding.java[ResolvedForwarding]

The immutable result. Each field carries a value only when it was present and honored:

[source,java]
----
record ResolvedForwarding(
    Optional<String> scheme,      // "http" | "https"
    Optional<String> host,        // host without port
    OptionalInt      port,        // 1..65535
    String           contextPath, // normalized prefix, "" when none / not honored
    Optional<String> clientIp)    // canonical client IP
----

`ResolvedForwarding.empty()` is the all-absent result a secure-by-default resolver returns for an
un-proxied or fully un-honored request.

=== xref:../cui-http-core/src/main/java/de/cuioss/http/forwarded/ForwardedResolverConfig.java[ForwardedResolverConfig]

Immutable trust-model configuration built through a validating builder. See xref:#trust-model[Trust model].

=== xref:../cui-http-core/src/main/java/de/cuioss/http/forwarded/ForwardedLogMessages.java[ForwardedLogMessages]

`HTTP-120`..`HTTP-127` WARN records (the package reserves `120`-`129`):

* `HTTP-120` / `HTTP-121` — a context path rejected for control characters, or for a
  protocol-relative / backslash prefix;
* `HTTP-122` — a forwarded value that failed sanitization;
* `HTTP-123` — a client-IP chain carrying an unparseable entry;
* `HTTP-124` (`FORWARDED_SOURCES_DISAGREE`) — a field dropped because the reconciled de-facto value
  and the RFC 7239 `Forwarded` header disagree;
* `HTTP-125` (`FORWARDED_DIRECTIVE_MALFORMED`) — a `Forwarded` header that carries a malformed
  `forwarded-pair` and so contributes nothing; only the fields whose directives the parser reached
  are suppressed (xref:adr/0021-Unresolvable_Forwarded_header_suppresses_only_the_fields_it_carried.adoc[ADR-0021]);
* `HTTP-126` (`TRUSTED_PROXY_ENTRY_BLANK`) — a blank `trustedProxies` entry ignored at
  configuration time;
* `HTTP-127` (`DE_FACTO_FAMILIES_DISAGREE`) — the `X-Forwarded-*` and `X-Proxy*` families disagreed
  and `deFactoPrecedence()` decided which one is honored; the field is kept, not dropped.

[#header-precedence]
== Header precedence

Scheme, host, port and client IP are *not* resolved by a first-present-wins order. Each source
family is resolved independently and the results are reconciled in two stages; only the context
path keeps an ordered first-present lookup:

[cols="1,4", options="header"]
|===
| Field | Sources and reconciliation

| scheme      | `X-Forwarded-Proto` reconciled with `X-ProxyScheme`, then against RFC 7239 `proto`
| host        | `X-Forwarded-Host` reconciled with `X-ProxyHost`, then against RFC 7239 `host` — host compared against host only
| port        | `X-Forwarded-Port` reconciled with `X-ProxyPort`, then against the port the RFC 7239 `host` directive carried; when no explicit port header is present, the port each source's `host[:port]` token carried, reconciled independently of the host
| contextPath | `X-ProxyContextPath` → `X-Forwarded-Prefix`, first present wins (RFC 7239 has no prefix directive → empty)
| clientIp    | `X-Forwarded-For` chain, reconciled against the RFC 7239 `for` chain
|===

*Stage 1 — the two de-facto families are reconciled against each other.* `X-Forwarded-*` and
`X-Proxy*` are two naming conventions for the same job, and a given deployment legitimately writes
one of them. When both are present and resolve to the same value, that value stands. When they
disagree the field is *not* dropped: the family named by `ForwardedResolverConfig.deFactoPrecedence()`
(default `X_FORWARDED`) wins and an `HTTP-127` warning is logged. That knob is a tie-breaker of last
resort, and it carries a deployment obligation: *the ingress must strip the family it does not
itself write.* An ingress that writes `X-Proxy*` and forwards a client-supplied `X-Forwarded-*`
unchanged has not removed the attack, only moved it behind a configuration setting.

*Stage 2 — the reconciled de-facto value is reconciled against RFC 7239 `Forwarded`*, as described
under *Conflicting sources* below.

*Repeated header instances are joined in wire order before token selection.* A proxy appends by
adding a repeated header line just as legitimately as by extending a comma-separated value, and
RFC 7230 §3.2.2 makes the two forms equivalent. The resolver therefore joins every instance the
accessor returns with `", "` in wire order, so a repeated header is indistinguishable from the
equivalent single comma-separated header before any token selection runs.

*Nearest hop wins within a header.* Each proxy in a chain *appends* its own value, so for a
comma-separated header value the resolver selects the *rightmost* token — the one contributed by the
closest, most trustworthy proxy. Leading tokens are attacker-supplied whenever the original client
sent the header itself. The same rule applies across RFC 7239 elements: the *last* `proto` / `host`
directive wins.

[source,text]
----
X-Forwarded-Proto: https, http                    -> scheme = http            (nearest hop appended "http")
X-Forwarded-Host:  attacker.example, app.internal -> host   = app.internal
X-Forwarded-Prefix: /app, /other                  -> prefix = /other
Forwarded: proto=https, proto=http                -> scheme = http            (last directive wins)
----

For the context-path the token selection must run *before* the injection guards, not after: a guard
applied to the whole raw string inspects only its leading characters, so `X-Forwarded-Prefix: /app,
//attacker.com` would pass the whole-string protocol-relative check and the nearest-hop token
`//attacker.com` would then be honored unguarded. Selecting the last token first means every guard
runs against the exact value that will be returned.

*Conflicting sources = drop (fail closed).* For scheme, host, port, and client IP the reconciled
de-facto value and the RFC 7239 `Forwarded` header are resolved *independently*. When only one
source is present its result is honored. When *both* are present they must agree: a proxy that
populates both families does not contradict itself, so a disagreement means at least one side is
forged. The field is then dropped and an `HTTP-124` warning logged, rather than letting either
source win by precedence — preferring one source is precisely what an attacker exploits by
supplying the family the resolver ranks higher.

*Host and port are independent fields.* A source states both in one `host[:port]` token, but the
token is compared field by field at both stages: a host disagreement drops only the host, and a port
disagreement drops only the port. A source that names a bare host says nothing about the port and
contests no port the other source carried. One exception keeps a forged value from being half
believed: when a host disagreement drops the host, a port that only the losing `host[:port]` token
carried is withheld too. An explicit `X-Forwarded-Port` / `X-ProxyPort` header supersedes the
host-token port and is reconciled against RFC 7239 on its own.

[source,text]
----
X-Forwarded-Proto: https + Forwarded: proto=https                -> scheme = https           (sources agree)
X-Forwarded-Proto: https + Forwarded: proto=http                 -> scheme = empty           (sources disagree -> dropped)
X-Forwarded-Proto: https                                         -> scheme = https           (single source, unaffected)
X-Forwarded-Host: h + X-Forwarded-Port: 8443 + Forwarded: host="h:8443"
                                                                 -> host = h, port = 8443    (agree field by field)
X-Forwarded-Host: h + X-Forwarded-Port: 8443 + Forwarded: host="h:9000"
                                                                 -> host = h, port = empty   (only the port disagrees)
----

*Present-but-invalid = empty resolution, not a fallback.* Each present, non-blank source is
validated. A source that fails its field guard still counts as present: it resolves to *nothing
valid*, and another source is *not* consulted in its place. What happens to that empty resolution
depends on the stage that compares it:

* *Stage 1 (de-facto families).* An empty resolution is compared like any other value, so when the
  sibling family resolved successfully the two disagree and `deFactoPrecedence()` breaks the tie
  (`HTTP-127`), exactly as for two valid but different values. If the selected family is the one
  that resolved to nothing valid, its empty resolution is selected: with the default `X_FORWARDED`
  precedence, `X-Forwarded-Proto: https` plus an invalid `X-ProxyScheme` resolves to `https`,
  whereas under `X_PROXY` precedence the same pair resolves to no scheme. The field is not dropped
  at this stage, and the unselected family's valid value is not used as a fallback.
* *Stage 2 (de-facto versus RFC 7239).* An empty resolution on one side and a valid value on the
  other is a disagreement, so the field is dropped (`HTTP-124`) under the fail-closed rule above.
* *Context path.* The ordered first-present lookup stops at the first present header, so a
  present-but-invalid `X-ProxyContextPath` yields an empty context path; `X-Forwarded-Prefix` is
  not consulted.

In particular a present-but-invalid
`X-Forwarded-Port` / `X-ProxyPort` (not digit-only, or outside `1..65535`) yields no port; the host
`:port` fallback is used only when *no* explicit port header is present at all. An IPv6 host must
likewise be supplied *bracketed* (`X-Forwarded-Host: [2001:db8::1]`) to be honored — an unbracketed
multi-colon value yields no host, because the host is composed back into a URL authority where an
unbracketed IPv6 literal is malformed and attacker-steerable. Content after the closing `]` is
rejected unless it is `:` plus the port, so `[::1]garbage` yields no host.

[#unresolvable-forwarded]
*An unresolvable `Forwarded` header suppresses only the fields it carried.* When the RFC 7239
`Forwarded` header's raw value fails sanitization, *or* when it carries a malformed
`forwarded-pair`, the header contributes *nothing*: it never supplies a value to the
reconciliation. Each field it *did* carry a directive for — as far as the parser got before it
stopped — therefore meets an empty RFC 7239 resolution and is dropped through the ordinary
disagreement path. Each field it carried *no* directive for is untouched, and the de-facto family
stands alone for it. A raw value that never sanitized yields no directives at all, so it suppresses
no field. A pair is malformed when it is non-blank and carries no `=`, an empty directive name, or an
empty value. Rejection is logged once as an `HTTP-125` warning with a log-sanitized value. The rule
and its trade-offs are recorded in
xref:adr/0021-Unresolvable_Forwarded_header_suppresses_only_the_fields_it_carried.adoc[ADR-0021].

RFC 7239 §4 defines `forwarded-element = [ forwarded-pair ] *( ";" [ forwarded-pair ] )`, so a pair
that is *blank* is grammatically legal: a trailing `;` is still accepted and parses normally.

[source,text]
----
X-Forwarded-Proto: https + X-Forwarded-Host: app.internal + Forwarded: proto=http;broken
                                                  -> scheme = empty, host = app.internal
                                                     (the parser reached proto, so only the scheme is suppressed)
X-Forwarded-Proto: https + Forwarded: broken;proto=http
                                                  -> scheme = https                (the parse stopped before proto)
X-Forwarded-Proto: https + Forwarded: proto=;host=app.internal
                                                  -> scheme = https                (the malformed first pair stops the parse; nothing was reached)
Forwarded: for=203.0.113.7;                       -> parses normally               (trailing ";" is a legal blank pair)
X-Forwarded-Port: 8080 + Forwarded: host="t.ex:9000";bad
                                                  -> port = empty                  (the host directive reached carried a port, so the port fails closed)
X-Forwarded-Port: 8080 + Forwarded: host=t.ex;bad -> port = 8080                   (that host directive stated no port)
----

[#trust-model]
== Trust model (secure by default)

The resolver honors nothing unless a deployment opts in. This is deliberate: a gateway may listen
on `0.0.0.0`, so a direct client can spoof forwarded headers to manipulate routing, the reflected
prefix in generated URLs, or the apparent client IP.

[cols="1,3", options="header"]
|===
| Setting | Effect

| `trustAll`
| Honor the sanitized `scheme` / `host` / `port` and any sanitized `contextPath`. Use only when
  the application sits fully behind a trusted proxy.

| `allowedContextPaths`
| Honor these specific normalized context paths even when `trustAll` is `false` (mirrors NiFi's
  `nifi.web.proxy.context.path` allowlist).

| `trustedProxies`
| CIDR ranges / IP literals (IPv4 + IPv6) defining trusted proxy hops. Required for
  `X-Forwarded-For` client-IP resolution — an empty set honors no client IP.
|===

With the secure default (`ForwardedResolverConfig.secureDefault()`: no allowlist, no trusted
proxies, `trustAll=false`), every forwarded value is ignored.

=== Client-IP resolution

The client IP is resolved by walking the `X-Forwarded-For` (or RFC 7239 `for`) chain
*right-to-left*, skipping hops that fall within `trustedProxies`; the first non-trusted,
well-formed address is the client. This prevents a spoofed prepended entry from being trusted.

* Sanitization happens *once, on the whole header value*, before the chain is split: the raw
  `X-Forwarded-For` value goes through the header-value pipeline as a single string and is only then
  split on commas. (The RFC 7239 `for` chain is covered the same way — the whole `Forwarded` value
  is sanitized once in `parseForwarded` before its directives are parsed.) Each resulting entry is
  then parsed as an IP literal (optional `:port` stripped, bracketed IPv6 unwrapped). Parsing is
  literal-only and never performs DNS resolution.
* Encountering an entry that is not a usable IP literal — an unparseable hop, or an RFC 7239
  `unknown` / obfuscated (`_hidden`) node identifier — *aborts the entire resolution*: the walk
  stops immediately and `clientIp` is empty. Such an entry is *not* skipped-and-continued, because a
  chain with an unverifiable hop cannot be trusted to identify the client. For example
  `Forwarded: for=203.0.113.7, for=unknown` yields an empty `clientIp` even though a well-formed
  address is also present.
* Two further shapes count as unusable literals and therefore abort the walk: content after the
  closing bracket of a bracketed IPv6 hop unless it is `:` plus digits (`[::1]garbage`,
  `[::1]:notaport`), and an IPv4 octet with a leading zero (`010.0.0.5`), which some resolvers read
  as octal and which is a classic allow-list bypass. A bare `0` octet remains valid.
* A malformed RFC 7239 `forwarded-pair` makes the `Forwarded` header unresolvable, so its `for`
  chain contributes nothing. The client IP is dropped only when the parser reached a `for`
  directive before it stopped; otherwise the `X-Forwarded-For` chain stands alone — see
  xref:#unresolvable-forwarded[An unresolvable `Forwarded` header suppresses only the fields it carried]
  (xref:adr/0021-Unresolvable_Forwarded_header_suppresses_only_the_fields_it_carried.adoc[ADR-0021]).
* An empty `trustedProxies` set or an all-trusted chain likewise yields an empty `clientIp`
  (fail-safe).

[source,text]
----
trustedProxies = [10.0.0.0/8]

X-Forwarded-For: 203.0.113.7, 10.0.0.5              -> clientIp = 203.0.113.7
X-Forwarded-For: 1.2.3.4, 203.0.113.7, 10.0.0.5     -> clientIp = 203.0.113.7  (spoofed 1.2.3.4 ignored)
X-Forwarded-For: 10.0.0.1, 10.0.0.5                 -> clientIp = empty         (all hops trusted)
X-Forwarded-For: 203.0.113.7, [::1]garbage          -> clientIp = empty         (trailing content -> walk aborts)
X-Forwarded-For: 010.0.0.5, 10.0.0.5                -> clientIp = empty         (leading-zero octet -> walk aborts)
(no trustedProxies configured)                       -> clientIp = empty         (nothing honored)
----

==== Composing `trustedProxies` — a range must contain only proxies

Membership of a `trustedProxies` range is a statement that the machine *is a proxy whose appended
chain entry can be believed* — not merely that it is on a network you own. The walk *skips* every
hop inside a configured range, so a range scoped to the enclosing VPC or office network rather than
to the proxy tier itself fails in both directions:

Too broad -> no client IP at all::
A range wide enough to cover the whole network (or `0.0.0.0/0`) makes *every* hop trusted, so the
walk skips the entire chain, falls off the left end, and returns empty. This fails closed — no
forged address is ever honored — but it is counter-intuitive to operators debugging a missing
client IP, who typically widen the range further and make the symptom worse.

Too broad -> client-IP spoofing::
A non-proxy machine that happens to fall inside a configured range is skipped by the walk exactly as
a real proxy would be. Anything that machine *prepends* to the chain is then treated as an earlier,
untrusted hop and returned as the client IP. One compromised or merely untrustworthy host inside the
range is enough to spoof the client IP for every request it forwards.

[source,text]
----
Deployment: ingress proxies at 10.0.7.10 and 10.0.7.11; application servers and a CI runner
            share the 10.0.0.0/8 network.

trustedProxies = [10.0.0.0/8]                       <1>
X-Forwarded-For: 6.6.6.6, 10.0.3.99, 10.0.7.10      -> clientIp = 6.6.6.6   (spoofed by 10.0.3.99)

trustedProxies = [10.0.7.10/32, 10.0.7.11/32]       <2>
X-Forwarded-For: 6.6.6.6, 10.0.3.99, 10.0.7.10      -> clientIp = 10.0.3.99 (the real peer)
----
<1> Too broad: the CI runner at `10.0.3.99` is inside the range, so the walk skips it and honors the
    entry it prepended.
<2> Correctly scoped to the proxy tier: `10.0.3.99` is untrusted, so the walk stops there and
    reports the address that actually connected to the proxy.

== Sanitization and injection guards

* Every honored value first passes through the header-value pipeline
  (xref:security-readme.adoc[Security Validation Framework]), which rejects over-length input, NUL
  (unless `allowNullBytes` is set), every other C0 control character except HTAB — CR/LF among
  them — unconditionally, the C1 range unconditionally, and extended ASCII / non-ASCII unless
  `allowExtendedAscii` is enabled (it defaults to `false`). The control-character rules do not
  depend on `allowControlCharacters` for header values — see
  xref:adr/0020-Header_and_cookie_character_gates_ignore_preset_flags_when_no_later_stage_can_re-check_them.adoc[ADR-0020].
* The *context-path* additionally rejects protocol-relative (`//host`) and backslash values, and
  this guard runs on the selected nearest-hop token. The header-value pipeline performs no path
  normalization (it has no `NormalizationStage`), so it neither collapses nor otherwise detects
  `//host`; this field guard is what rejects it. Honoring `//attacker.com` would compose into a
  protocol-relative URL (`//attacker.com/...`) in the browser and exfiltrate the request.
* The context-path is normalized to exactly one leading slash and no trailing slash; a slash-only
  value collapses to empty.
* The *host* is checked against an allow-list grammar: an unbracketed host must be dot-separated
  labels built only from ASCII letters, digits, `-` and `_` (neither at a label's start or end, at
  most 63 characters per label and 253 in total), and a bracketed host must contain an IP literal.
  Every other character is therefore rejected — the path separator, backslash, whitespace, and the
  URL-authority delimiters `@`, `#` and `?` among them; an embedded `@` would otherwise let a
  forged host smuggle a userinfo component into a composed URL. A trailing `:port` is split into
  the port field. The *port* is honored only within `1..65535`. The *scheme* is lowercased and
  honored only when it is `http` or `https`.

=== Configuring the sanitization

The header-value pipeline is *configurable* through the `securityConfig` of
`ForwardedResolverConfig` (default `SecurityConfiguration.defaults()`), but only through the four
xref:security-readme.adoc[`SecurityConfiguration`] knobs the pipeline actually consumes:

* `maxHeaderValueLength` — enforced by `LengthValidationStage`.
* `allowNullBytes`, `allowControlCharacters`, `allowExtendedAscii` — read by
  `CharacterValidationStage`; for a header value `allowControlCharacters` no longer widens
  anything, because every C0 control except HTAB is rejected regardless of it (ADR-0020).

Every other knob has *no effect* on forwarded sanitization. `PipelineFactory.createHeaderValuePipeline`
builds a `HEADER_VALUE` pipeline of `LengthValidationStage` + `CharacterValidationStage` only — no
`DecodingStage`, no `NormalizationStage`, no `PatternMatchingStage`, and `AllowBlockListStage` is
added for `HEADER_NAME` only. So `normalizeUnicode`, `allowDoubleEncoding`,
`failOnSuspiciousPatterns`, and the header allow/block lists never run against a forwarded header
value, and `SecurityConfiguration.strict()` / `.lenient()` change forwarded behaviour only through
the four knobs above.

[source,java]
----
ForwardedResolverConfig config = ForwardedResolverConfig.builder()
    .trustAll(true)
    .securityConfig(SecurityConfiguration.strict())   // tighten header-value sanitization
    .build();
----

The *field-specific* guards, by contrast, are fixed fail-secure invariants and are *not* affected
by `securityConfig`: the context-path protocol-relative (`//`) and backslash rejection, the
context-path comma/whitespace rejection, the `http`/`https` scheme whitelist, the `1..65535` port
range, and host-separator rejection always apply.

The context-path comma/whitespace rejection is defence in depth: a well-formed context path
contains neither, so their presence in a value that reached normalization means a comma-separated
header value arrived without nearest-hop token selection having been applied — and normalizing such
a value would honor an attacker-supplied token.

== Serialization

`ResolvedForwarding` can be emitted back as proxy headers — useful when forwarding a request
upstream and for round-trip testing.

[source,java]
----
Map<String,String> toXForwardedHeaders()   // X-Forwarded-Proto/-Host/-Port/-Prefix/-For (present fields only)
Optional<String>   toForwardedHeader()      // single RFC 7239 Forwarded value: for=…;host=…;proto=…
----

[IMPORTANT]
====
*Asymmetry:* RFC 7239 `Forwarded` has no prefix/context-path directive, so `contextPath` is
expressible only through `X-Forwarded-Prefix` (via `toXForwardedHeaders()`), never through
`toForwardedHeader()`. IPv6 client addresses are bracketed and quoted per RFC 7239; other values
are quoted only when they are not a valid RFC 7239 token.
====

== Usage Examples

=== Fully behind a trusted proxy

[source,java]
----
ForwardedResolverConfig config = ForwardedResolverConfig.builder()
    .trustAll(true)                                          // honor scheme/host/port + context-path
    .trustedProxies(Set.of("10.0.7.10/32", "10.0.7.11/32"))  // the ingress proxies themselves
    .build();

ForwardedHeaderResolver resolver =
    new ForwardedHeaderResolver(config, new SecurityEventCounter());

// The accessor MUST expose every instance of a repeated header, not just the first.
// Passing the socket peer makes the resolver honor nothing unless it is a trusted proxy:
ResolvedForwarding fwd = resolver.resolve(
    name -> Collections.list(request.getHeaders(name)),
    InetAddress.getByName(request.getRemoteAddr()));

// An absent scheme means no proxy attested one - possibly because a disagreement dropped it.
// Decide that case explicitly (here: the scheme of the connection that actually reached this
// server); never default to a hard-coded cleartext scheme.
String scheme = fwd.scheme().orElseGet(request::getScheme);
String host   = fwd.host().orElse(request.getServerName());
int    port   = fwd.port().orElseGet(request::getServerPort);
String prefix = fwd.contextPath();          // "" when none
fwd.clientIp().ifPresent(ip -> log.info("client %s", ip));
----

NOTE: `trustedProxies` lists the proxy machines themselves, never the enclosing network — see
_Composing `trustedProxies`_ above. Widening this to the surrounding `10.0.0.0/8` would let any
host inside that range spoof the client IP.

=== Context-path allowlist only (no trustAll)

[source,java]
----
// Honor only /app and /gateway as reverse-proxy prefixes; ignore everything else.
ForwardedResolverConfig config = ForwardedResolverConfig.builder()
    .allowedContextPaths(Set.of("/app", "/gateway"))
    .build();

ForwardedHeaderResolver resolver =
    new ForwardedHeaderResolver(config, new SecurityEventCounter());

String prefix = resolver
    .resolve(name -> Collections.list(request.getHeaders(name)))
    .contextPath();
----

The allowlist may also be parsed from an operator-supplied comma-separated string:

[source,java]
----
Set<String> allowed = ForwardedResolverConfig.parseAllowlist("/app, /gateway/");
----

=== Secure default (honors nothing)

[source,java]
----
ForwardedHeaderResolver resolver = new ForwardedHeaderResolver(
    ForwardedResolverConfig.secureDefault(), new SecurityEventCounter());

// Any forwarded header is ignored; result is ResolvedForwarding.empty()
ResolvedForwarding fwd =
    resolver.resolve(name -> Collections.list(request.getHeaders(name)));
----

== Thread Safety

`ForwardedHeaderResolver`, `ForwardedResolverConfig`, and `ResolvedForwarding` are immutable and
thread-safe. A single resolver instance can be shared across requests and threads.
