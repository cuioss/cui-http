== Findings
=== F-D-1: The two de-facto families (X-Forwarded-* vs. NiFi X-Proxy*) are NOT reconciled — a fixed precedence hands one of them to the attacker
* Severity: High
* Category: security-gap / false-security
* Status: CONFIRMED (probe)
* Location:
** /home/user/cui-http/cui-http-core/src/main/java/de/cuioss/http/forwarded/ForwardedHeaderResolver.java:191 (`+firstPresent(lookup, X_FORWARDED_PROTO, X_PROXY_SCHEME)+`), :211 (`+X_FORWARDED_HOST, X_PROXY_HOST+`), :333 (`+X_FORWARDED_PORT, X_PROXY_PORT+`), :385 (`+X_PROXY_CONTEXT_PATH, X_FORWARDED_PREFIX+`)
** doc/adr/0002-…adoc:125-129 ("any *fixed* precedence answers that question in a way the attacker can predict and exploit")
* Evidence (probe output, `+trustAll=true+`):
----
  XFPrefix=/app (proxy) + X-ProxyContextPath=/evil (attacker)      => /evil
  X-ProxyScheme=http (proxy) + X-Forwarded-Proto=https (attacker)   => Optional[https]
  X-ProxyHost=app.example.com (proxy) + X-Forwarded-Host=attacker.example => Optional[attacker.example]
  X-ProxyPort=443 (proxy) + X-Forwarded-Port=8080 (attacker)        => OptionalInt[8080]
----
* Analysis: ADR-0002 and the class Javadoc (lines 96-104) argue that a fixed precedence between two independently-writable header sources is exploitable, and implement fail-closed reconciliation between the de-facto family and RFC 7239 `+Forwarded+`. The *same* situation exists between `+X-Forwarded-*+` and `+X-Proxy*+`, but here `+firstPresent+` simply takes the first present name. Consequences for a deployment whose proxy manages exactly one of the two families (which is every real deployment — nginx/Traefik/SCG write `+X-Forwarded-*+`, NiFi writes `+X-Proxy*+`) and does not explicitly blank the other:
** Traefik/SCG deployment (`+X-Forwarded-Prefix+` from the proxy): an unauthenticated client adds `+X-ProxyContextPath: /evil+` and wins, because `+X-ProxyContextPath+` has *higher* precedence (line 385). Generated absolute links/redirects get an attacker-chosen path prefix on the trusted host.
** NiFi deployment (`+X-ProxyHost+`/`+X-ProxyScheme+` from the proxy): the client adds `+X-Forwarded-Host: attacker.example+` and wins → the classic password-reset-link / cache-poisoning host injection that the whole reconciliation design was introduced to prevent. Whichever family the operator's proxy uses, the *other* one is attacker-winnable. Nothing in the docs tells the operator to strip the unmanaged family (grep for strip/overwrite in doc + Javadoc finds nothing).
* Recommendation: Treat `+X-Proxy*+` as a third source in `+reconcileSources+` (present-and-agreeing or dropped), exactly like the RFC source. Alternatively/additionally add a config knob restricting which families are consulted (e.g. `+Builder.honoredFamilies(EnumSet)+`), and state in the docs that every non-managed header of the family MUST be removed at the ingress proxy. Add regression tests mirroring `+SourceDisagreement+` for the de-facto siblings.

=== F-D-2: "Fail closed" on disagreement is attacker-triggerable and, for the scheme, fails toward `+http+` — one bogus `+Forwarded+` header wipes every resolved field
* Severity: High
* Category: false-security / security-gap
* Status: CONFIRMED (probe + existing tests)
* Location:
** ForwardedHeaderResolver.java:505-516 (`+parseForwarded+` → `+UNRESOLVABLE_RESULT+`), :330 (`+if (forwarded.unresolvable()) return OptionalInt.empty()+`), :558-572 (`+reconcileSources+`)
** doc/forwarded-header-resolution.adoc:449, package-info.java:84, ResolvedForwarding.java:44 — all three usage examples read `+fwd.scheme().orElse("http")+`
** doc/adr/0002:167-171 (frames the negative only as "a partially-upgraded proxy chain")
* Evidence (probe, proxy correctly sets XFF/Proto/Host/Port with `+trustAll=true+`, `+trustedProxies=10.0.0.0/8+`):
----
  proxy sets XFF/Proto/Host/Port, attacker adds Forwarded: garbage =>
    ResolvedForwarding[scheme=Optional.empty, host=Optional.empty, port=OptionalInt.empty, contextPath=, clientIp=Optional.empty]
  XFF clean + attacker Forwarded: for=unknown  => Optional.empty
  XFF clean + attacker Forwarded: for=9.9.9.9  => Optional.empty
  XFF long attacker prefix (2700 chars) + proxy-appended real ip => Optional.empty   (sanitize() rejects the whole joined XFF > 2048)
----
* Analysis: The resolver never verifies the socket peer (see F-D-3), so *any* client can add a `+Forwarded+` header (or 2 KB of junk in front of its `+X-Forwarded-For+`). Unless the proxy strips inbound `+Forwarded+`, the client can at will:
.. Suppress its own client-IP attribution (rate-limiting, audit logs, geo/IP allow-lists all see "no IP").
.. Null the scheme. Every documented consumer pattern is `+scheme().orElse("http")+`, so the documented fail-closed path fails *open* in the security-relevant direction: absolute URLs, OAuth `+redirect_uri+`, cookie `+Secure+` decisions, HSTS logic derived from the resolved scheme silently downgrade to `+http+`. Under the pre-ADR fixed precedence this specific downgrade was impossible (proxy XFP won).
.. Null the host and port, so the app falls back to `+request.getServerName()+` (doc line 450) — often the internal service name, leaking it into generated links. The docs call this "fail closed" without ever stating the precondition that makes it safe: the trusted proxy MUST strip or overwrite `+Forwarded+` (and, per F-D-1, the unmanaged de-facto family). The `+SecurityConfiguration.maxHeaderValueLength+` (2048) additionally turns "fail closed" into a one-header DoS of IP attribution because the *whole joined* XFF value is length-checked (line 440) before the walk.
* Recommendation: (a) Document, in the MANDATORY warning box and the class Javadoc, that the ingress proxy must remove every client-supplied header of all three families it does not itself set — this is the actual precondition for the fail-closed logic to be a defence rather than an attacker lever. (b) Offer `+honoredFamilies+` so single-family deployments can ignore `+Forwarded+` entirely. (c) Change the three `+orElse("http")+` examples to `+orElse("https")+` or to an explicit "treat empty scheme as an error" pattern, and say why. (d) For the client IP, consider length-checking per chain entry (or after taking the rightmost N entries) instead of the joined header, so an attacker-supplied prefix cannot invalidate the proxy-appended hop.

=== F-D-3: `+trustedProxies+` never gates whether headers are believed — the peer address is not an input, so the trust model cannot be implemented as documented ("trust only if the request came through a trusted proxy")
* Severity: Medium
* Category: false-security
* Status: CONFIRMED (probe + code)
* Location: ForwardedHeaderResolver.java:52-63 (Javadoc admits it), :171 (`+resolve(Function<String, List<String>>)+` — only input), :435-437 (only check: `+config.trustedProxies().isEmpty()+`)
* Evidence (probe): `+direct attacker, XFF: 6.6.6.6 (no proxy hop at all) => Optional[6.6.6.6]+` with `+trustedProxies=10.0.0.0/8+`.
* Analysis: `+trustedProxies+` only decides which XFF hops to *skip*; it never decides whether the header may be believed at all. The industry-standard algorithm (Spring `+ForwardedHeaderFilter+`+RemoteIpValve, Express `+trust proxy+`, Traefik `+forwardedHeaders.trustedIPs+`) refuses all forwarded headers when the socket peer is outside the trusted set. The Javadoc says this is "by design", but the design pushes the single most important check to "network controls" the library cannot verify, while the option name `+trustedProxies+` promises exactly that check. Combined with F-D-2, an attacker who can reach the listener directly does not merely spoof the IP — they choose every field.
* Recommendation: Add `+resolve(Function<String,List<String>> headerLookup, @Nullable InetAddress peer)+`; when a peer is supplied and is not inside `+trustedProxies+`, return `+ResolvedForwarding.empty()+` (and log once at WARN). Keep the current overload for transports that cannot provide the peer, but mark it clearly as the weaker variant.

=== F-D-4: Host reconciliation compares host *and* port, so a proxy that legitimately emits both families drops the host while keeping the port
* Severity: Medium
* Category: correctness
* Status: CONFIRMED (probe)
* Location: ForwardedHeaderResolver.java:213-216 (`+reconcileSources("host", …, hostPortOf(...), hostPortOf(...))+`), :567 (`+fromDeFacto.equals(fromRfc)+` on `+Optional<HostPort>+`), :701 (`+record HostPort(Optional<String> host, OptionalInt port)+`)
* Evidence (probe):
----
  XFH=app.example.com  XFPort=8443  Forwarded: host="app.example.com:8443"
     => host=Optional.empty, port=OptionalInt[8443]
  XFH=app.example.com:8443  Forwarded: host=app.example.com
     => host=Optional.empty, port=OptionalInt.empty
----
* Analysis: A proxy that puts the port in `+X-Forwarded-Port+` (the de-facto convention) and folds it into RFC 7239 `+host="name:port"+` (the only place RFC 7239 can carry it) is *not* contradicting itself, yet the record-equality on `+HostPort+` reports a disagreement and drops the host — producing a result with a port but no host. Conversely the port is never reconciled against the RFC host's port at all (`+resolvePort+` ignores `+Forwarded+` except for the unresolvable flag), so a genuine port disagreement (`+X-Forwarded-Port: 80+` vs `+Forwarded: host="x:8443"+`) is silently resolved in favour of the de-facto header. Inconsistent with the ADR-0002 promise that each field is reconciled independently.
* Recommendation: Reconcile `+host+` on the host string only; reconcile `+port+` as its own field taking `+X-Forwarded-Port+`/`+X-ProxyPort+` vs the RFC `+host+` port (falling back to the de-facto host port when no explicit port header exists). Add tests for both of the shapes above.

=== F-D-5: Host validation is a 6-character deny-list; quotes, `+<>+`, `+;+`, `+%+`, `+]+`, and non-ASCII homoglyph hosts are honored
* Severity: Medium
* Category: security-gap
* Status: CONFIRMED (probe)
* Location: ForwardedHeaderResolver.java:306-314 (`+containsHostSeparator+`: only `+/ \ @ # ?+` + whitespace), :259-300 (`+parseHostPort+`); SecurityConfigurationBuilder.java:97 (`+allowExtendedAscii = true+` default) + CharacterValidationStage.java:422 (`+HEADER_VALUE -> true+` Unicode)
* Evidence (probe, `+trustAll=true+`):
----
  Forwarded host="abc (unbalanced quote)  => Optional["abc]
  XFH exаmple.com (Cyrillic а)            => Optional[exаmple.com]
  XFH example.com%2Fpath                  => Optional[example.com%2Fpath]
  XFH example.com;x                       => Optional[example.com;x]
  XFH <b>                                 => Optional[<b>]
  XFH "quoted"                            => Optional["quoted"]
  XFH ex]ample                            => Optional[ex]ample]
----
* Analysis: `+ResolvedForwarding+` Javadoc promises fields are "normalized and injection-guarded"; consumers compose `+host+` into absolute URLs, `+Location+` headers and HTML. A homoglyph host (IDN look-alike) is the canonical phishing host for password-reset poisoning and passes because the default `+SecurityConfiguration+` allows Unicode in header values. `+%2F+` and `+;+` produce authorities most URL parsers reject or split differently; `+<b>+` is a stored-XSS payload if any consumer reflects the host. The bracketed branch validates its content as an IP literal, but the unbracketed branch never validates the host as an RFC 3986 `+reg-name+`.
* Recommendation: Replace the deny-list with an allow-list: unbracketed host must match `+[A-Za-z0-9](?:[A-Za-z0-9-]*[A-Za-z0-9])?(\.[A-Za-z0-9](?:[A-Za-z0-9-]*[A-Za-z0-9])?)*\.?+` (ASCII, punycode `+xn--+` labels allowed), or be a valid IPv4 literal; otherwise `+HostPort.EMPTY+` + WARN. Optionally add an `+allowedHosts+` set to `+ForwardedResolverConfig+` (the standard mitigation for host-header attacks).

=== F-D-6: Context-path guard does not reject `+?+`, `+#+`, `+;+`, dot-segments or percent-encoded slashes
* Severity: Low
* Category: security-gap
* Status: CONFIRMED (probe)
* Location: ContextPaths.java:44-57 (`+normalize+` checks only control chars, `+//+`, `+\+`, `+,+`, whitespace); ForwardedHeaderResolver.java:402-425
* Evidence (probe, `+trustAll=true+`): `+/app/../admin => /app/../admin+`, `+/app?x=1 => /app?x=1+`, `+/app#f => /app#f+`, `+%2F%2Fattacker.com => /%2F%2Fattacker.com+`, `+/аpp (Cyrillic) => /аpp+`.
* Analysis: The prefix is concatenated by consumers as `+scheme://host + contextPath + "/path?query"+`. A `+?+` or `+#+` inside the prefix turns the remainder of the composed URL into query/fragment (path confusion, breaks `+redirect=+` parameters); `+..+` re-points generated links to sibling paths on the same host (`+/app/../admin/reset?token=…+`). Same-host only, hence Low — but the library ships a `+NormalizationStage+` and never applies it here, while the doc calls the value "normalized".
* Recommendation: Reject `+?+`, `+#+`, `+%2F+`/`+%5C+` (case-insensitive), and any `+.+`/`+..+` segment (or run the RFC 3986 dot-segment normalizer and reject if it changes the value). Consider requiring ASCII.

=== F-D-7: Stale/incorrect rationale: "the header-value pipeline collapses `+//host+` to `+/host+`" — it does not
* Severity: Low
* Category: documentation / consistency
* Status: CONFIRMED (probe)
* Location: ForwardedHeaderResolver.java:392-394 (comment "the header-value pipeline collapses a protocol-relative "//host" prefix to "/host", masking the attack"); doc/forwarded-header-resolution.adoc:366-368 (same claim); contradicted by the same doc at lines 386-396 ("LengthValidationStage + CharacterValidationStage only — no NormalizationStage") and by HTTPHeaderValidationPipeline.java:144-146.

* Recommendation: Rewrite the comment/doc: the guard runs first so the WARN is emitted against the raw nearest-hop token, and `+normalize+` re-applies the same guard after sanitization as defence in depth.

=== F-D-10: Port-suffix parsing asymmetry: `+1.2.3.4:abc+`, `+1.2.3.4:+` and `+example.com:abc+` are accepted while `+[::1]:abc+` is rejected; invalid host-carried port is dropped silently instead of dropping the value
* Severity: Low
* Category: consistency / correctness
* Status: CONFIRMED (probe)
* Location: IpAddresses.java:130-132 (single-colon branch takes `+token.substring(0, indexOf(':'))+` and never inspects the suffix; bracket branch line 126 enforces `+hasValidBracketTrailer+`); ForwardedHeaderResolver.java:283-284 (host kept, `+parsePort+` failure ignored).
* Evidence (probe): `+parseChainEntry("1.2.3.4:abc") => 1.2.3.4+`, `+parseChainEntry("1.2.3.4:") => 1.2.3.4+`, `+XFH example.com:abc => host=example.com, port=empty+`, `+XFH example.com: => host=example.com+`.
* Analysis: The Javadoc/doc state the rule "present-but-invalid = drop (no fall-through)" and the bracket trailer rule was made shared precisely so the two policies "cannot drift apart" — yet the unbracketed branch applies no such rule. Not a bypass (the address itself is validated), but a documented invariant that does not hold.
* Recommendation: In both places, require the text after the single colon to be all-ASCII-digits (reuse `+hasValidBracketTrailer(":" + suffix)+`); return null / `+HostPort.EMPTY+` otherwise.

=== F-D-11: IPv4-mapped IPv6 forms bypass the leading-zero-octet rejection and other IPv4 literal rules
* Severity: Info
* Category: consistency
* Status: CONFIRMED (probe)
* Location: IpAddresses.java:43 (`+IPV6_LITERAL = "[0-9A-Fa-f:.]+"+`), :74-84 (`+parse+`)
* Evidence: `+parseChainEntry("::ffff:010.0.0.5") => 10.0.0.5 (Inet4Address)+` whereas `+parseChainEntry("010.0.0.5") => null+`; `+::ffff:0a00:0005+`, `+0:0:0:0:0:ffff:10.0.0.5+`, `+[::ffff:10.0.0.5]:443+` all collapse to `+10.0.0.5+` and match a `+10.0.0.0/8+` trusted range.
* Analysis: The outcome is a canonical, unambiguous IPv4 address, so this is not exploitable; but the "leading-zero octet is rejected outright" claim (IpAddresses.java:29-31, doc line 303) is only true for the dotted-quad spelling. Also `+::10.0.0.5+` (deprecated IPv4-compatible) stays a 16-byte address and never matches an IPv4 range — fail-closed, fine, but undocumented.
* Recommendation: Either document the mapped-form behaviour next to the leading-zero rule, or reject `+.+`-bearing IPv6 literals whose embedded IPv4 part fails `+IPV4_LITERAL+`.

=== F-D-12: `+RfcForwardedParser+` tolerates duplicate parameters inside one element although RFC 7239 §4 forbids it — inconsistent with "a malformed pair rejects the whole header"
* Severity: Low
* Category: correctness / consistency
* Status: CONFIRMED (probe)
* Location: RfcForwardedParser.java:121-127 (`+case "for" -> forValues.add(value)+`, `+proto+`/`+host+` overwritten silently); Javadoc lines 45-52 claims grammar violations mark the header malformed.
* Evidence: `+Forwarded: for=1.2.3.4;for=10.0.0.5+` → treated as a two-hop chain → `+clientIp=1.2.3.4+`; `+proto=https;proto=http+` → `+http+`.
* Analysis: RFC 7239 §4: "Each parameter MUST NOT occur more than once per forwarded-element". A parser that rejects `+proto=+` as malformed but accepts a duplicate `+for=+` is enforcing the grammar selectively. Not a trust bypass on its own (the attacker already controls leading elements), but a duplicate `+for+` in a single element synthesises a hop that no proxy appended.
* Recommendation: Track parameter names per element and return `+MALFORMED_RESULT+` on a repeat.

=== F-D-13: `+sanitizeForLog+` does not neutralise Unicode line/paragraph separators or bidi controls
* Severity: Low
* Category: security-gap
* Status: CONFIRMED (code)
* Location: ForwardedHeaderResolver.java:644-651 (`+Character.isISOControl(c) ? '?' : c+`)
* Analysis: `+isISOControl+` covers U+0000–U+001F and U+007F–U+009F only. Header values may contain U+2028/U+2029 (accepted by the HEADER_VALUE character stage, which allows Unicode by default) and U+202E (RTL override); many log viewers treat U+2028 as a newline, re-enabling the log-forging the method exists to prevent.
* Recommendation: Also replace `+Character.getType(c)+` in {LINE_SEPARATOR, PARAGRAPH_SEPARATOR, FORMAT} or restrict to printable ASCII.

== Verified strengths
* CidrRange: `+/0+`, `+/32+`, `+/128+`, sub-byte prefixes (`+/28+`, `+/31+`, `+/127+`), negative and over-range prefixes, family mismatch, IPv4-mapped spec bound (32) all behave correctly (probe section 5); masking in `+parse+` and `+contains+` are consistent (CidrRange.java:103-133).
* IpAddresses: no DNS lookup is reachable — `+IPV4_LITERAL+` bounds octets, `+IPV6_LITERAL+` + JDK 21 `+getAllByName+` throws `+UnknownHostException+` for any colon-bearing non-literal (verified `+::ffff:999.1.1.1+` → null, `+fe80::1%eth0+` → null, `+0x7f.0.0.1+` → null, `+1.2.3+` → null).
* Bracket trailer rule is genuinely shared (`+hasValidBracketTrailer+`, IpAddresses.java:158) and covered on both call sites by tests.
* Nearest-hop (rightmost) selection is applied uniformly to every field incl. the RFC accumulator (ADR-0001 is implemented as described; ForwardedHeaderResolver.java:635-638, RfcForwardedParser.java:121-124).
* Multi-instance accessor contract (ADR-0003): `+joining()+` (ForwardedHeaderResolver.java:474-486) joins in wire order once at the boundary; blank/null instances are handled (`+['', '203.0.113.7, 10.0.0.5']+` → correct).
* The three-state Forwarded model (absent / present / unresolvable) is implemented exactly as documented, including the port (ForwardedHeaderResolver.java:330, 505-516, 676-696).
* `+ContextPaths.normalize+` re-applies the `+//+`/backslash/control-char guards after sanitization, so the stale rationale in F-D-7 has no security consequence.
* `+ResolvedForwarding+` compact constructor enforces the stated invariants (CR/LF unconstructible, port range, scheme allow-list, normalized prefix), so serialization cannot re-inject headers; `+quoteIfNeeded+` escapes `+\+` and `+"+` correctly.
* Header-value sanitization: HTAB is allowed (an interior tab in XFF does not suppress the client IP — probe), CR/LF/NUL rejected, 2048-char limit enforced.
* Interior `+,+`/whitespace defence in `+ContextPaths+` and the "token selection before guards" ordering work (`+/app, //attacker.com+` → "" with WARN, covered by ForwardedTrustBoundaryTest).
* LogMessages.adoc forwarded table (HTTP-120..126) matches `+ForwardedLogMessages+` identifiers, levels and template text exactly.
