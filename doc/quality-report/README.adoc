== Method

=== Why a multi-agent review

The repository holds roughly 19,000 lines of production Java, 46,000 lines of test Java, and 8,500 lines of AsciiDoc. No single reviewer can hold that in working memory, and a security library deserves adversarial reading rather than skimming. The review was therefore decomposed into units small enough to be read completely, each unit was reviewed through one or more lenses by an independent reviewer, and every finding was then handed to a separate adversarial verifier whose instruction was to refute it.

=== Lenses

* *code* -- correctness for all inputs including edge cases, fail-closed behaviour on every error path, hidden traps where a name or Javadoc promises more than the code delivers, Javadoc accuracy, concurrency claims, regex and allocation hazards.
* *tests* -- whether each test asserts a specific outcome or merely exercises code, whether every security control has both a rejecting and an accepting test, untested edge cases (which were then probed against the real code), correct and deterministic use of `cui-test-generator`, compliance with the project's own testing standards.
* *test infrastructure* -- attack databases and generators are shipped in the published `generators` classifier and are therefore product code: do they contain what they claim, are they consumed, are their consumers' assertions strong, is anything duplicated or dead.
* *docs* -- the code is ground truth; every class name, method, example, default, count, cross-reference and claim in a document was checked against it.
* *cross-cutting* -- grep-driven sweeps that no single unit can see: fail-open paths, duplicated content, coverage data, build and CI.

=== Verification

Every finding produced by a reviewer was passed, in batches of at most five, to a separate verifier agent that had not seen the reviewer's reasoning. Its instruction was to refute: open the cited location, reproduce behavioural claims by running the compiled classes in `jshell`, search the whole test tree before accepting a "missing test" claim, check ADRs and Javadoc for a documented deliberate decision, and re-assess severity. Verdicts are:

* `CONFIRMED` -- the claim holds as stated.
* `PARTIALLY_CONFIRMED` -- the core claim holds but a detail or the severity was corrected; the corrected title is shown.
* `UNVERIFIABLE` -- could not be reproduced in the review environment (for example, requires the network); kept with the reviewer's evidence.
* `UNVERIFIED` -- the verifier did not return a verdict for this item (agent failure); kept and marked.
* `REFUTED` -- the claim does not hold; listed in the area report's transparency section only.

After the reports were written, an independent agent with a clean context read them and re-verified the findings end to end. Its results are in xref:adversarial-verification.adoc[adversarial-verification.adoc].

=== Tooling

* Static reading of every file in scope, with `grep -n` for cross-references.
* `jshell` against the compiled `target/classes` and `target/test-classes` plus the full dependency classpath, used to feed concrete inputs to pipelines, stages, the forwarded resolver, adapters and TLS providers and to record the actual output.
* The JUnit Platform console launcher to run individual compiled test classes without Maven.
* JaCoCo XML from `verify -Pcoverage` for the coverage figures.
* Maven was run once for the baseline (test and coverage) before the review started and not during it, so the compiled classes reviewed are exactly those of the reviewed commit.

=== Severity scale

[cols="1,5", options="header"]
|===
| Severity | Meaning

| CRITICAL | Exploitable security gap, a security control that fails open, or silent data corruption.
| HIGH | A real bug; a false sense of security likely to bite users; a missing negative test for a security control; a documented feature that does not exist.
| MEDIUM | Misleading documentation or Javadoc; an edge-case bug with limited impact; a coverage-only test; a missing edge-case test.
| LOW | Inconsistency, duplication, ambiguity, or deviation from the project's own written standards.
| INFO | An observation worth recording, including positive ones.
|===

=== Limitations

* Network-dependent behaviour (real TLS handshakes against public hosts, proxy behaviour) could not be exercised; those claims are marked `UNVERIFIABLE` where a verifier could not reproduce them.
* The review is of a snapshot. Findings reference line numbers of the reviewed commit.
* Reviewer and verifier agents read independently; the same underlying issue can occasionally surface under two identifiers from two units. Such pairs are cross-referenced in the register where noticed.
* The benchmarking module was reviewed for correctness and consistency, not for the validity of its published performance numbers.
