== Consolidation notes

This document is review stream E (`F-E-`), covering the security test framework under `cui-http-core/src/test/java/de/cuioss/http/security/{generators,database,tests}` and the documents that describe it. Test-quality findings for the *other* packages are in the respective area documents (client: F-client-7, F-client-8, F-client-18; forwarded: F-D-19; pipelines and stages: F-B-14 and the `F-A-` test items).

* F-E-1 and F-E-2 are the two most important findings on the test side (proposed High, recorded Medium after the adversarial verification because they are test-quality rather than runtime defects). Together they mean that the test classes named after header injection, request smuggling and URL-length attacks establish nothing about those mechanisms, and that several "legitimate input" tests cannot fail. Both were reproduced by the lead reviewer's own probe (`/api?x=y` is rejected on the `?` before decoding runs).
* F-E-5 answers the question "are generators used correctly": most attack "generators" wrap fixed literal lists and are *sampled* with a per-run random seed, so individual entries are skipped on most runs. The probabilities quoted were recomputed by the lead reviewer and are correct (coupon-collector arithmetic).
* F-E-6 exposes a production consequence: base64 cookie values with `+`, `/` or `=` are rejected by `CharacterValidationStage(COOKIE_VALUE)` (the set is RFC 3986 unreserved, not RFC 6265 `cookie-octet`), and no valid generator is wide enough to reveal it. See also L-5 in xref:01-security-validation.adoc[].
* F-E-8 and F-E-9 overlap F-documentation-7 and F-documentation-8; the document-side view is kept there.
* The inventories at the end of this document (validator-to-test matrix, generator inventory with draw counts, attack-database inventory) are the answer to the review question "are there always positive and negative tests" and should be read as the baseline for any test-suite clean-up.

== Findings

=== F-E-1: URL-shaped "header injection / smuggling / length" attack tests are rejected on the literal `+?+` (or space/`+#+`), never on the mechanism they claim to test
* Severity: Medium (reviewer proposed High; adjusted after adversarial verification — a test-quality defect, not a runtime one, on the report's own scale)
* Category: false-security
* Status: CONFIRMED (executed)
* Location:
** `+cui-http-core/src/test/java/de/cuioss/http/security/tests/HttpHeaderInjectionAttackTest.java:102-123+` (150 generated URLs), `+:128-159+`, `+:162-185+`, `+:187-214+`, `+:216-238+`, `+:262-291+`, `+:293-320+`, `+:322-344+`
** `+cui-http-core/src/test/java/de/cuioss/http/security/tests/HttpRequestSmugglingAttackTest.java:235-257+` and the six guarded tests `+:268-452+` which even `+assertEquals(UrlSecurityFailureType.INVALID_CHARACTER, ...)+` (`+:286+`, `+:319+`, `+:352+`, `+:384+`, `+:416+`, `+:448+`)
** `+cui-http-core/src/test/java/de/cuioss/http/security/tests/Http1VulnerabilitiesTest.java:110-470+` (10 of 11 methods use payloads containing `+?+` and/or a literal space)
** `+cui-http-core/src/test/java/de/cuioss/http/security/tests/URLLengthLimitAttackTest.java:273-306+` (query overflow), `+:316-349+` (repeated params), `+:402-435+` (long parameter names), `+:445-478+` (buffer overflow incl. `+/resource#...+` at `+:462+`), `+:488-520+`, `+:530-563+`
** Generators feeding them: `+generators/header/HttpHeaderInjectionAttackGenerator.java:77-83+` (every `+BASE_URLS+` entry is an absolute URL) + `+:105,119,133,...+` (every branch appends `+"?<name>=" + attack+`); `+generators/injection/HttpRequestSmugglingAttackGenerator.java:65-71+` and every pattern array (`+pattern + "?data=..."+`).
* Evidence (probe run against `+URLPathValidationPipeline(SecurityConfiguration.defaults())+`):
----
  </api?x=y>                                                    -> INVALID_CHARACTER : Invalid character '?' (0x3F) at position 4
  <http://example.com/redirect?redirect=normal%0d%0aX-Injected: malicious> -> INVALID_CHARACTER : Invalid character '?' (0x3F) at position 27
  <http://example.com/api/data?data=test%0d%0aContent-Length: 6%0d%0aTransfer-Encoding: chunked> -> INVALID_CHARACTER : '?' at position 27
  </api?data=chunked%0d>                                        -> INVALID_CHARACTER : '?' at position 4
  </api%0d%0aGET /admin HTTP/1.1>                               -> INVALID_CHARACTER : Invalid character ' ' (0x20) at position 13
  </data?query_string_parameter_name_abc=search>                -> INVALID_CHARACTER : '?' at position 5
  </search?param=abc>  (maxParameterValueLength=256)            -> INVALID_CHARACTER : '?' at position 7
  </resource#frag>                                              -> INVALID_CHARACTER : '#' at position 9
  </api%0d%0aX-Injected:malicious>  (no '?', no space)          -> CONTROL_CHARACTERS : Decoded control character (U+000D) at position 4
----
  `+CharacterValidationConstants+` `+RFC3986_PATH_CHARS+` contains neither `+?+` nor `+#+` nor space, and `+CharacterValidationStage+` runs before `+DecodingStage+` in `+URLPathValidationPipeline.createStages+`. `+HttpRequestSmugglingAttackTest.java:487+` even documents the wrong expectation: `+// - CRLF injection (%0d%0a, %0a) → CONTROL_CHARACTERS or INVALID_CHARACTER+`.
* Analysis: Every value emitted by `+HttpHeaderInjectionAttackGenerator+` and `+HttpRequestSmugglingAttackGenerator+` contains a `+?+`, so all 158 + 1435 surefire cases in T15/T16 are decided at the `+?+` before the encoded CRLF is ever decoded. Deleting `+DecodingStage.validateDecodedCharacters+` (the only place a `+%0d%0a+` in a path is caught) would leave `+HttpHeaderInjectionAttackTest+`, `+HttpRequestSmugglingAttackTest+` and `+Http1VulnerabilitiesTest+` green. Likewise in `+URLLengthLimitAttackTest+` the "parameter value/name over limit" assertions are satisfied by the `+?+` regardless of length (the entry documented as `+// ~49 chars total - within STRICT+` at `+:419+` is still rejected, which the test then reports as a detected length attack). The `+isURLLengthLimitSpecificFailure+` helper hides this by accepting `+INVALID_CHARACTER+` with the comment `+// Repeated chars in length attacks+` (`+:665+`). The analysis doc built on these tests (see F-E-8) therefore claims coverage ("25 CL.TE-specific tests", "553 tests") that establishes nothing about CRLF or smuggling handling.
* Recommendation: (1) Feed header-injection payloads to the surface that actually receives header values: `+HTTPHeaderValidationPipeline(HEADER_VALUE)+` with raw `+\r\n+` (that is what `+HTTPHeaderInjectionGenerator+` is for) and `+URLParameterValidationPipeline+` with the percent-encoded query *value* only (strip the URL scaffolding in the generators or add a `+queryValue()+` accessor). (2) For the path pipeline, use path-only payloads (`+/api%0d%0aX:y+`) and assert `+CONTROL_CHARACTERS+` exactly. (3) Add a differential guard to each attack test: the same payload with the attack bytes removed must be ACCEPTED by the pipeline under test; otherwise the test is not testing the attack. (4) In `+URLLengthLimitAttackTest+` drive parameter-length cases through `+URLParameterValidationPipeline+`/`+URLParameterNameValidationPipeline+` and assert `+INPUT_TOO_LONG+` exactly.

=== F-E-2: Accept-or-reject tests that cannot fail on validator behaviour
* Severity: Medium (reviewer proposed High; adjusted after adversarial verification — same reasoning as F-E-1)
* Category: test-quality
* Status: CONFIRMED (traced)
* Location / Evidence:
.. `+tests/EncodedPathTraversalAttackTest.java:137-153+` — `+shouldHandleLegitimateEncodedCharacters+` draws from `+EncodingCombinationGenerator+` (an *attack* generator whose own contract test asserts every value is rejected, `+generators/encoding/EncodingCombinationGeneratorTest.java:67-69+`), names it `+legitimatePattern+`, and `+catch (UrlSecurityException e) { // This is acceptable ... }+` with no assertion. Passes for any pipeline behaviour.
.. `+tests/DoubleEncodingAttackTest.java:200-225+` — `+shouldValidateValidPaths+` (`+ValidURLPathGenerator+`): `+catch (UrlSecurityException e) { // Some paths might still be blocked ... This is acceptable ... assertTrue(initialEventCount < eventCounter.getTotalCount()) }+`. A pipeline that rejects every legitimate path passes.
.. `+tests/DoubleEncodingAttackTest.java:235-274+` — `+shouldHandleEdgeCases+`: 12 literals, each either accepted (asserts `+isPresent+`) or rejected (`+// This is acceptable - either for security reasons or invalid encoding+`). No literal has an expected outcome.
.. `+tests/NullBytePathTraversalAttackTest.java:94-120+` — `+shouldProcessBoundaryFuzzingPatternsCorrectly+` (75 draws): accepted → `+isPresent+`, rejected → `+assertNotNull(e.getFailureType())+`. Zero information about which inputs must be rejected; `+BoundaryFuzzingGenerator+` families 2–5 (null bytes, control chars, traversal, shell metachars) are all "must reject" inputs.
.. `+tests/CookieChaosAttackTest.java:362-396+` — Test #8 validates 200 `+AttackCookieGenerator+` draws and asserts only that *at least one* name and *at least one* value were rejected (`+isRejected+` swallows the exception at `+:405-412+`). A `+CharacterValidationStage+` that rejected only `+\t+` would pass. The Javadoc (`+:353-360+`) states this is deliberate because the generator emits an empty name — the fix is to make the generator's contract precise (F-E-12), not to weaken the assertion.
.. `+tests/CookieChaosAttackTest.java:246-289, 305-325+` — Tests #5/#6 ("documentation") assert only that the `+Cookie+` record stores attributes; no validator is invoked although `+CookiePrefixValidationStage.validateCookie(Cookie)+` exists and would reject exactly these cookies (`+validation/CookiePrefixValidationStage.java+`, `+validateHostPrefix+`/`+validateSecurePrefix+`). The class Javadoc (`+:60-66+`) still says prefix semantics are "not yet implemented in the library", contradicting `+doc/http-security/analysis/cookie-chaos-analysis.adoc:76-85+` ("FULLY MITIGATED", 71 tests).
.. `+tests/EncodedPathTraversalAttackTest.java:175-200+` — `+shouldHandleEdgeCases+` is the one honest variant (it `+fail()+`s if an accepted value contains `+..+`/`+\0+`/control chars) but still accepts any rejection reason.
* Analysis: Items 1–4 are the classic "if rejected ok, if accepted also ok" pattern the brief asks about; items 5–6 are weaker variants. Together they inflate the surefire count (75 + 20 + 20 + 1 + 1 + 1 + 1 cases) without constraining behaviour, and item 2/3 in particular mask false positives on legitimate paths (the exact regression class the `+Legitimate*Database+` tests exist to catch).
* Recommendation: Delete 1 (it duplicates `+shouldRejectAllGeneratedEncodedPatterns+`); make 2 a hard `+assertPipelineAccepts+` (the sibling `+MixedEncodingAttackTest.java:200-218+` already does this for the same generator); give each literal in 3 an explicit expected verdict (`+%25+` and `+/normal%25path+` → accepted; `+%+`, `+%2+`, `+%252G+` → `+INVALID_ENCODING+`; `+%25252e+`, `+%2525%252e%252e%252f+`, `+/%25%25%25%25%25+` → `+DOUBLE_ENCODING+`); split 4 by family (long-path/deep-nesting families → accepted or `+PATH_TOO_LONG+`/`+EXCESSIVE_NESTING+`, the other four families → must reject); rewrite 5 per draw once F-E-12 is fixed; turn 6 into `+assertThrows+` against `+new CookiePrefixValidationStage().validateCookie(...)+` with `+COOKIE_PREFIX_VIOLATION+`.

=== F-E-3: Failure-type assertions are "any of 6–10 of the 24 enum values" — labelled as the opposite
* Severity: Medium
* Category: test-quality
* Status: CONFIRMED
* Location: `+tests/PathTraversalAttackTest.java:234-250+` (7 types), `+tests/DoubleEncodingAttackTest.java:283-295+` (9), `+tests/MixedEncodingAttackTest.java:228-240+` (9), `+tests/NullBytePathTraversalAttackTest.java:279-292+` (10), `+tests/HttpRequestSmugglingAttackTest.java:485-501+` (7), `+tests/Http1VulnerabilitiesTest.java:478-485+` (6), `+tests/URLLengthLimitAttackTest.java:654-667+` (10), `+tests/UnicodeControlCharacterAttackTest.java:540-549+` (6), `+tests/UnicodeNormalizationAttackTest.java:509-522+` (10), `+tests/UnicodePathTraversalAttackTest.java:192-201+` (6), `+tests/ProtocolHandlerAttackTest.java:396-409+` (three category predicates plus 7 literals; `+SUSPICIOUS_PATTERN_DETECTED+` listed twice at `+:402+` and `+:405+`), `+tests/CookieChaosAttackTest.java:133-134+` (`+failureType.name().contains("CHARACTER") || ...contains("CONTROL")+`).
* Evidence: every helper carries the Javadoc `+QI-9: ... Replaces broad OR-assertion with comprehensive security validation+` while being exactly a broad OR (e.g. `+NullBytePathTraversalAttackTest+` accepts `+PATH_TOO_LONG+`, `+INPUT_TOO_LONG+`, `+EXCESSIVE_NESTING+`, `+DOUBLE_ENCODING+` for a null-byte generator whose every value contains `+\0+`/`+%00+`).
* Analysis: With `+CharacterValidationStage+` first in the pipeline, `+INVALID_CHARACTER+` is accepted by all eleven helpers, so any non-ASCII / non-path character anywhere in the payload satisfies them. Combined with F-E-1 this is why the suite cannot distinguish "the attack mechanism was detected" from "the payload was malformed". Contrast with the database tests, which assert `+assertEquals(testCase.expectedFailureType(), ...)+`.
* Recommendation: Per test method, assert the exact type the generator branch guarantees (e.g. `+NullByteURLGenerator+` → `+NULL_BYTE_INJECTION+` for all 15 entries; `+PathTraversalParameterGenerator+` → `+PATH_TRAVERSAL_DETECTED+`; `+UnicodeAttackGenerator+` bare arms → `+PATH_TRAVERSAL_DETECTED+`, invisible-char arms → `+INVALID_CHARACTER+`). Where a generator mixes branches, classify the draw in the test (as `+HttpRequestSmugglingAttackTest+` already does with regex guards) and assert per class.

=== F-E-4: "Protocol handler" database and generator exercise protocol-handler detection in 1 of 24 entries / ~0 of the generated values
* Severity: Medium
* Category: false-security
* Status: CONFIRMED (database verdicts are asserted exactly by `+ProtocolHandlerAttackDatabaseTest+`; generator traced)
* Location: `+database/ProtocolHandlerAttackDatabase.java:59-235+`, `+generators/injection/ProtocolHandlerAttackGenerator.java:339-348+` (`+generatePath()+` — every option starts with `+../+` or `+/../+`), `+tests/ProtocolHandlerAttackTest.java:106-129+`.
* Evidence: declared types in the database: `+PATH_TRAVERSAL_DETECTED+` ×16, `+INVALID_CHARACTER+` ×5, `+NULL_BYTE_INJECTION+` ×1, `+CONTROL_CHARACTERS+` ×1, `+SUSPICIOUS_PATTERN_DETECTED+` ×1 (`+JAVASCRIPT_ENCODED_EVAL+`, `+:66-71+`). The rationales say so themselves ("traversal detection takes precedence over the javascript: scheme content", `+:63+`). In `+PatternMatchingStage.validate+`, step 1 (traversal) throws before step 3 (`+checkProtocolHandlerSchemes+`), and every generator branch except `+generateProtocolHandlerExploitation+` case 1 / `+generateCustomProtocolSchemes+` case 1 embeds `+../+`. Probe: `+<javascript:alert(1)>+` is ACCEPTED under `+SecurityConfiguration.defaults()+` (failOnSuspiciousPatterns=false) — no test in this tree exercises that default.
* Analysis: The database name, class Javadoc ("Protocol Attack Categories … JS Protocol Injection, Data URI …") and `+ProtocolHandlerAttackTest+` Javadoc claim coverage of scheme detection that the payloads never reach. Give `+ProtocolHandlerAttackGenerator+` a traversal-free arm and assert `+SUSPICIOUS_PATTERN_DETECTED+` for it.

=== F-E-5: Fixed-list generators are randomly sampled with a fresh random seed, so entries are skipped on most runs
* Severity: Medium
* Category: generator-usage
* Status: CONFIRMED (javap + arithmetic)
* Location: `+generators/url/NullByteURLGenerator.java:63-79+` (15 literals via `+Generators.fixedValues+`), `+generators/url/NullByteInjectionParameterGenerator.java:27-42+` (14 literals), `+generators/header/HttpHeaderInjectionAttackGenerator.java+` (15 families × 7 literals × 5 base URLs = 525 fixed strings), `+generators/injection/HttpRequestSmugglingAttackGenerator.java+` (525 fixed strings); consumers `+tests/NullBytePathTraversalAttackTest.java:133,165,199,227,254+` (25/50/25/20/22 draws), `+pipeline/URLParameterValidationPipelineTest.java:134+` (5 draws of 14), `+pipeline/URLPathValidationPipelineTest.java:122+` (5 of 15), `+tests/HttpHeaderInjectionAttackTest.java:103+` (150 of 525), `+tests/HttpRequestSmugglingAttackTest.java+` (200 of 525).
* Evidence: `+FixedValuesGenerator.next()+` = `+values.get(RandomContext.random().nextInt(size))+`; `+RandomContext.initSeed()+` = `+random.nextLong()+` → the seed is random per JVM run unless `+@GeneratorSeed+`/`+-Dde.cuioss.test.generator.seed+` is set (no `+@GeneratorSeed+` anywhere in the tree). Coverage per run (coupon-collector): 15 entries / 25 draws → E[distinct]=12.3, P(all 15)=2.2 %; 15/20 → 0.2 %; 14 entries / 5 draws → ≤5 exercised; 525/150 → ~131 distinct (25 %); 525/200 → ~166 (32 %); `+SupportedValidationTypeGenerator+` 4 values / 5 draws in `+PipelineFactoryTest.java:210+` → P(all 4)=23 %.
* Analysis: A `+TypedGenerator+` over a closed literal list adds randomness without adding coverage: a regression that breaks exactly one literal is detected only probabilistically. `+NullByteURLGenerator+`'s Javadoc (`+:26-32+`) even argues these literals must be preserved exactly — which is the argument for iterating them exhaustively.
* Recommendation: Expose the literal lists as `+static final List<String>+` and drive `+@ParameterizedTest @MethodSource+` (or `+@FieldSource+`) over them deterministically; keep `+TypedGenerator+` for spaces that are genuinely combinatorial (`+PathTraversalGenerator+`, `+URLLengthLimitAttackGenerator+`). For the 525-string smuggling/header-injection corpora, iterate the arrays directly (the arrays are already static per family) and reserve the random draw for the base-URL prefix if at all.

=== F-E-6: "Valid" generators are too narrow to detect false positives, and two of them are not valid for any pipeline
* Severity: Medium
* Category: generator-usage
* Status: CONFIRMED (executed for the cookie case)
* Location: `+generators/cookie/ValidCookieGenerator.java:228-231+` (`+letterStrings(...).toUpperCase()+`), contract `+generators/cookie/ValidCookieGeneratorTest.java:50+` (`+COOKIE_TOKEN = "[A-Za-z0-9_]+"+`); `+generators/url/ValidURLParameterGenerator.java+` (values ∈ {digits, true/false, asc/desc, 4 formats, 5 langs, 4 statuses, 4 words}); `+generators/url/ValidURLGenerator.java:43-54,70+` (emits `+/search?q=test&limit=10+` and appends `+?page=..&sort=..+` in 50 % of draws); `+generators/url/ValidURLGeneratorTest.java:59-64+` (accepts query syntax); `+generators/url/InvalidURLGenerator.java:103+` (`+protocol + "://" + host + "/" + path + "/"+` — a well-formed URL); `+generators/header/ValidHTTPHeaderValueGenerator.java:245-252+` (`+Origin+` values `+same-origin+`/`+no-cors+`, which are Fetch request modes, not `+Origin+` header syntax).
* Evidence: probe with `+CharacterValidationStage(COOKIE_VALUE)+`: `+abc+/=+` → `+INVALID_CHARACTER '+'+`; `+YWJjZGVm==+` → `+INVALID_CHARACTER '='+`; i.e. base64 session tokens (RFC 6265 `+cookie-octet+` permits `++ / = ! # $ % & ' ( ) * : < > ? @ [ ] ^ { | } ~+`) are rejected, and no valid-generator value can reveal it because the generator only emits `+[A-Za-z0-9_]+`. `+ValidURLGenerator+` values with `+?+` are rejected by `+URLPathValidationPipeline+` (probe `+</api?x=y>+` → `+INVALID_CHARACTER+`), and the generator is consumed only by `+AllGeneratorsIntegrationTest+` (grep) — never against a pipeline. `+InvalidURLGenerator+` likewise has no pipeline consumer; its own test admits well-formed output ("so that this test states honestly what the generator emits today", `+InvalidURLGeneratorTest.java:41-43+`).
* Analysis: The false-positive side of the contract ("valid generators only produce inputs that MUST be accepted") is satisfied trivially by staying inside the smallest accept set; that gives no signal about over-rejection of realistic input (a security library that rejects every base64 cookie value is a production-blocking false positive). `+ValidURLGenerator+`/`+InvalidURLGenerator+` are dead weight relative to the pipelines.
* Recommendation: Widen `+ValidCookieGenerator+` values to the RFC 6265 `+cookie-octet+` alphabet (or at least base64 tokens) and make its pipeline round-trip assert acceptance (or record the rejection as a production finding for the owner of `+CharacterValidationConstants+`); widen `+ValidURLParameterGenerator+` to percent-encoded values (as `+ValidURLParameterStringGenerator+` already does) and consolidate the two; either split `+ValidURLGenerator+` into path and query parts and route them to the matching pipelines or delete it together with `+InvalidURLGenerator+`; replace the bogus `+Origin+` values with `+https://example.com+`/`+null+`.
