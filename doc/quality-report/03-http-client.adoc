=== F-client-1: ETag cache hands one principal's cached body to another principal as "fallback content" once `+Authorization+` is excluded from the cache key — exactly the configuration the docs recommend
* Severity: High
* Category: false-security / security-gap
* Status: CONFIRMED (line-by-line trace; every referenced line quoted)
* Location:
** `+adapter/ETagAwareHttpAdapter.java:1135-1142+` (key/entry lookup), `+:608-611+` (foreign ETag sent as `+If-None-Match+`), `+:986-996+` (fallback decision)
** `+adapter/CacheKeyHeaderFilter.java:14-15+`, `+:103-107+`, `+:19-32+`
** `+adapter/ETagAwareHttpAdapter.java:127-143+` (class-level "Token Refresh" example), `+:1229-1234+` (Builder recommendations)
** `+adapter/package-info.java:115-133+`, `+client/package-info.java:271-294+`
** `+doc/http-result-pattern.adoc:100-105+`, `+:209-213+`
* Evidence:
[source,java]
----
  // ETagAwareHttpAdapter.java:1139-1142
  String cacheKey = generateCacheKey(httpHandler.getUri(), headers, cacheKeyHeaderFilter);
  return new CacheContext<>(cacheKey, cache.get(cacheKey));
  // :608-609
  if (cachedEntry != null && method == HttpMethod.GET) {
      requestBuilder.setHeader("If-None-Match", cachedEntry.etag());
  // :987-995
  boolean canUseCachedFallback = method == HttpMethod.GET && cachedEntry != null;
  return HttpResult.<T>failureWithFallback(
          "HTTP %d: %s".formatted(statusCode, method.methodName()), null,
          canUseCachedFallback ? cachedEntry.content() : null, ...
          canUseCachedFallback ? cachedEntry.etag() : null, statusCode);
----
[source,java]
----
  // CacheKeyHeaderFilter.java:14-15
  * This functional interface allows fine-grained control beyond simple all-or-nothing
  * choices, solving the token refresh cache bloat problem while maintaining security.
  // :106-107 (excluding(...))
  * <p><b>Solves token refresh cache bloat</b> by excluding Authorization
----
----
  // http-result-pattern.adoc:102-104
  // Use fallback if available
  result.getContent().ifPresent(fallback ->
      logger.warn("Using cached fallback content"));
----
* Analysis: The fallback branch at `+:987+` is gated on *method == GET and a cache entry exists*, not on *who* populated the entry or on the error class. With `+CacheKeyHeaderFilter.excluding("Authorization")+`, `+NONE+`, or any `+including(...)+` that omits `+Authorization+` — all of which the Javadoc actively recommends for "token refresh" — the key is identical for every principal calling the same URI. Concrete scenario, fully traced through the code: (1) user A, `+Authorization: Bearer A+`, GET → 200 + ETag → `+putInCache(key, contentA)+` (`+:945-948+`). (2) user B, `+Authorization: Bearer B+`, same adapter → `+prepareCacheContext+` yields `+cachedEntry = contentA+` → the request carries `+If-None-Match: <A's ETag>+` (`+:608+`). (3) Server answers `+403+` (B is not authorised) → `+handleHttpResponse+` reaches `+:986-996+` with `+canUseCachedFallback == true+` → B receives `+HttpResult.Failure+` whose `+getContent()+` is *A's body* and `+getETag()+` is A's validator. The project's own consumption guidance (`+http-result-pattern.adoc:100-105+`, `+:209-213+`, `+HttpResult.java:76-86+`) tells callers to use `+getContent()+` on a failure as degraded content, so a caller following the docs serves A's data to B. The only caveat in the codebase is one bullet in `+Builder#cacheKeyHeaderFilter+` ("Multi-user shared adapters: Use default ALL for security", `+:1232+`) and the `+NONE+` Javadoc's "may cache wrong content" (`+:97+`); neither mentions that a *4xx authorisation failure* is answered with the *other user's content*, and `+excluding("Authorization")+` is explicitly sold as "maintaining security" (`+:15+`). Secondary, present even with `+ALL+`: a token that has expired/been revoked but is still presented unchanged hits the same key, gets `+401+`, and the adapter returns the cached body as fallback — the client keeps "reading" a resource its credential no longer grants. The "Failure with fallback" state was designed around `+503, using cached JWKS+` (`+HttpResult.java:291-298+`); the code applies it to every non-2xx/304 status including 401/403/404/410.
* Recommendation: (a) Restrict fallback to retryable / availability failures: `+canUseCachedFallback = method == GET && cachedEntry != null && errorCategory.isRetryable()+` (SERVER_ERROR only from the status path; NETWORK_ERROR is handled in `+.exceptionally+` at `+:690-704+` and today gets *no* fallback at all — the opposite of what the docs describe). Never surface fallback for 401/403. (b) Make credential-bearing headers part of the *entry identity* even when they are excluded from the *key*: store e.g. a SHA-256 of the `+Authorization+` value in `+CacheEntry+` and treat a mismatch as "no entry" (no `+If-None-Match+`, no fallback). (c) Rewrite the `+CacheKeyHeaderFilter+` / class-level / package-info "token refresh" guidance to state the leak explicitly and restrict the recommendation to single-principal adapters. (d) Add an integration test: two `+Authorization+` values, second one answered 403, assert `+getContent().isEmpty()+` and that no `+If-None-Match+` was sent.

=== F-client-2: "Only hostname verification is relaxed" is over-stated — the `+null+`-engine delegation also drops TLS-level algorithm constraints and stapled OCSP responses
* Severity: Medium
* Category: documentation / false-security
* Status: CONFIRMED (against JDK 21u source)
* Location:
** `+handler/HostnameVerificationRelaxingTrustManager.java:281-297+` (esp. `+:294-296+`), `+:401-403+`
** `+handler/SecureSSLContextProvider.java:177-182+`
** `+handler/HttpHandler.java:197-203+`, `+:1038-1046+` (`+verifyHostname+` Javadoc)
** `+doc/client-handlers-readme.adoc:56-67+`
** `+doc/adr/0007-*.adoc:43-51+`, `+:75-78+`
* Evidence (project):
[source,java]
----
  // HostnameVerificationRelaxingTrustManager.java:294-296
  *   <li>revocation posture - whatever revocation checking the delegate is configured for still applies</li>
  *   <li>algorithm constraints - the JDK's disabled-algorithm and key-size policies still apply</li>
  // :401-403
  public void checkServerTrusted(X509Certificate[] chain, String authType, SSLEngine engine) ... {
      delegate.checkServerTrusted(chain, authType, (SSLEngine) null);
----
  Evidence (JDK 21u, `+sun/security/ssl/X509TrustManagerImpl.java+`, engine overload, lines 257-297):
[source,java]
----
  if (engine != null) {
      ... constraints = SSLAlgorithmConstraints.forEngine(engine, localSupportedSignAlgs, false);
      ... responseList = ((ExtendedSSLSession)session).getStatusResponses();
      trustedChain = v.validate(chain, null, responseList, constraints, ...);
      ... checkIdentity(session, trustedChain, identityAlg, checkClientTrusted);
  } else {
      trustedChain = v.validate(chain, null, Collections.emptyList(), null, ...);
  }
----
  `+sun/security/validator/PKIXValidator.java:218-220+`: `+if (constraints != null) { pkixParameters.addCertPathChecker(new AlgorithmChecker(constraints, variant)); }+`.
* Analysis: With a `+null+` engine the JDK skips more than `+checkIdentity+`. It passes `+constraints = null+` (so `+SSLAlgorithmConstraints+` — which merges `+jdk.tls.disabledAlgorithms+`, any `+SSLParameters.setAlgorithmConstraints(...)+` the client set, and the "peer certificate signature must be among the locally supported signature schemes" check for TLS 1.2+ — is *not* added as a `+CertPathChecker+`), and passes an empty `+responseList+` (so stapled OCSP responses from the handshake are discarded). What survives is only what `+PKIXCertPathValidator+` applies on its own: chain trust, validity period, and `+jdk.certpath.disabledAlgorithms+`. In JDK 21 defaults the two disabled-algorithm lists overlap heavily, so the practical exposure is small today, but the statements "algorithm constraints … still apply" and "revocation posture … unchanged" are not literally true: a deployment that enables revocation checking and relies on OCSP stapling (`+jdk.tls.client.enableStatusRequestExtension+`) will, under `+verifyHostname(false)+`, silently fall back to a live OCSP/CRL fetch or, with hard-fail, to a handshake failure — a behaviour change the caller was told does not happen. ADR-0007 (`+:75-78+`) states the mechanism "performs no logic of its own beyond substituting the engine/socket argument", which is accurate; the *consequence* of that substitution is what the ADR and all Javadoc understate.
* Recommendation: Correct the four documentation sites to say: "skips endpoint identification; additionally, because the platform trust manager receives no `+SSLEngine+`, the TLS-layer algorithm constraints (`+jdk.tls.disabledAlgorithms+`, `+SSLParameters.setAlgorithmConstraints+`, signature-scheme conformance) and stapled OCSP responses are not consulted — certificate-path constraints (`+jdk.certpath.disabledAlgorithms+`), chain trust and validity remain enforced." Add the stapled-OCSP point to ADR-0007 "Risks". If the stricter behaviour is wanted, a wrapper can re-apply the constraints itself: call `+delegate.checkServerTrusted(chain, authType, (SSLEngine) null)+` and then run `+new AlgorithmChecker(SSLAlgorithmConstraints.forEngine(engine, false), ...)+` over the chain — but that pulls in `+sun.security.*+` internals, so the documentation fix is the realistic one.

=== F-client-3: 301/302 rewrite every non-GET/HEAD method to GET (RFC 9110 sanctions only POST→GET; the JDK preserves the method) — a redirected DELETE/PUT is reported as a *successful* DELETE/PUT after issuing a GET
* Severity: Medium
* Category: correctness
* Status: CONFIRMED (line-by-line trace; not exercised by any test)
* Location: `+handler/HttpHandler.java:780-804+` (`+rebuildForHop+`), Javadoc `+:763-766+`; consumer at `+adapter/ETagAwareHttpAdapter.java:688-689+`, `+:976-977+`
* Evidence:
[source,java]
----
  // HttpHandler.java:782-784
  boolean preserveMethodAndBody = statusCode == 307 || statusCode == 308;
  boolean bodylessMethod = METHOD_GET.equals(method) || METHOD_HEAD.equals(method);
  boolean dropBody = !preserveMethodAndBody && !(statusCode != 303 && bodylessMethod);
  // :796-800
  if (!preserveMethodAndBody && (statusCode == 303 || !bodylessMethod)) {
      // GET() also clears the body publisher carried over from the original request.
      builder.GET();
  }
----
  RFC 9110 §15.4.2/§15.4.3: "For historical reasons, a user agent MAY change the request method from POST to GET for the subsequent request." (POST only). JDK 21u `+jdk/internal/net/http/RedirectFilter.java:89-97+`: `+case 301, 302 -> orig.equals("POST") ? "GET" : orig; case 303 -> "GET"; case 307, 308 -> orig;+` — the JDK keeps the original method on 301/302 unless it is POST.
* Analysis: For `+DELETE+`, `+PUT+`, `+PATCH+`, `+OPTIONS+` the condition `+!bodylessMethod+` is true, so a 301/302 turns the request into a body-less `+GET+` at the new location. Through `+ETagAwareHttpAdapter+`, `+adapter.delete()+` → 301 → GET → 200 with a body → `+handleHttpResponse(method=DELETE, 200)+` → `+HttpResult.success(...)+`: the caller is told the delete succeeded although nothing was deleted, and a `+PUT+` body is silently discarded while the PUT is reported as success. 303 additionally rewrites `+HEAD+` to `+GET+` (`+statusCode == 303+` short-circuits `+bodylessMethod+`), so `+pingHead()+` following a 303 downloads a body; RFC 9110 §15.4.4 permits either GET or HEAD and the JDK's `+RedirectFilter+` makes the same HEAD→GET choice (`+:92+`), so that part is a defensible design choice rather than a defect — only the PUT/DELETE/PATCH/OPTIONS→GET rewrite on 301/302 deviates from both the RFC and the JDK. The Javadoc (`+:763-766+`) documents the behaviour, but that does not make it correct, and the redirect tests only cover POST→GET (`+HttpHandlerRedirectTest.java:490-503+`) and GET/HEAD preserved (`+:558-572+`); there is no DELETE/PUT/PATCH case and no HEAD-on-303 case.
* Recommendation: Rewrite only `+POST+` to `+GET+` on 301/302 (`+boolean rewriteToGet = statusCode == 303 ? !METHOD_HEAD.equals(method) : METHOD_POST.equals(method)+`), keep every other method and its body (as for 307/308); optionally keep HEAD on 303 (RFC-permitted; the JDK does not). Add parameterised tests for `+{301,302} × {PUT,DELETE,PATCH}+` asserting the method reaches the target unchanged, and a `+303 × HEAD+` case pinning whichever choice is made.

=== F-client-9: `+RedirectPolicy.forwardsCredentials+` returns `+true+` for *any* cross-origin https target under `+FORWARD_TO_ALLOWLISTED+`, ignoring the allowlist
* Severity: Low
* Category: false-security (API footgun; not exploitable through `+HttpHandler+`)
* Status: CONFIRMED (probe 1a/1b)
* Location: `+handler/RedirectPolicy.java:212-216+`; Javadoc `+:199-202+`; guard that currently prevents impact: `+handler/HttpHandler.java:745-748+`
* Evidence:
[source,java]
----

      if (SCHEME_HTTP.equals(asciiLowerCase(to.getScheme()))) { return false; }

----
  Probe: `+forwardsCredentials(https://api.example.com/a, https://evil.example.org/b)+` with allowlist `+[cdn.example.net]+` and `+FORWARD_TO_ALLOWLISTED+` → `+true+`; `+refuse(...)+` → `+CROSS_ORIGIN+`.

=== F-client-12: HEAD reads the cache but the adapter never makes a HEAD conditional — the documented "HEAD 304" branch is reachable only through a header the same Javadoc tells callers not to send
* Severity: Low
* Category: consistency
* Status: CONFIRMED
* Location: `+adapter/ETagAwareHttpAdapter.java:1000-1015+` (`+canReadCache+`), `+:608+` (`+If-None-Match+` for GET only), `+:57-65+` ("Do not supply your own If-None-Match"), `+:1107-1109+`

=== F-client-13: `+StringContentConverter+` silently mis-decodes when the server writes `+charset = X+` (whitespace around `+=+`)

=== F-client-15: Cache key embeds raw credential values and the cache has no TTL or byte bound
* Severity: Info
* Category: security-gap
* Status: CONFIRMED
* Location: `+adapter/ETagAwareHttpAdapter.java:731-754+` (key = URI + `+header:value+` for every included header), `+:805-812+`, `+:852-881+`, `+:1164+` (default 1000 entries)
* Analysis: With the default `+ALL+` filter the literal `+Authorization: Bearer …+` value is part of the `+String+` key kept in the `+ConcurrentHashMap+` for as long as the entry lives (until 1000 entries overflow; no time-based expiry). * Recommendation: Hash header values (SHA-256) into the key; add an optional max-age; document the memory model.

== Verified strengths

* *TLS floor is real on the wire*: `+HttpHandler.java:441-452+` pins `+SSLParameters.setProtocols(provider.getEnabledProtocols())+` → `+[TLSv1.2, TLSv1.3]+` or `+[TLSv1.3]+`; `+SecureSSLContextProvider.java:126-132+` never returns anything older; asserted in `+HttpHandlerTest.java:147-170+` and `+SecureSSLContextProviderTest.java:105-120+`. TLS 1.0/1.1 cannot be offered by this client.
* *No trust-all anywhere*: `+createSecureSSLContext()+` / `+createHostnameRelaxedSSLContext()+` (`+SecureSSLContextProvider.java:153-205+`) use `+TrustManagerFactory.init((KeyStore) null)+` (JVM default store); the relaxing wrapper only wraps `+X509ExtendedTrustManager+` instances and forwards everything else verbatim (`+HostnameVerificationRelaxingTrustManager.java:349-359+`). Chain trust, expiry and not-yet-valid rejection under the wrapper are proven with real handshakes (`+HostnameVerificationRelaxingTrustManagerTest.java:83-131+`), with a matched negative control (`+:71-82+`).
* *Relaxation is opt-in and loud*: only `+verifyHostname(false)+` reaches `+createHostnameRelaxedSSLContext()+` (`+HttpHandler.java:1288-1292+`), always logs HTTP-116, is rejected with a caller-supplied `+sslContext+` (`+:1211-1216+`), survives `+asBuilder()+` only via the package-private `+derivedSslContext+` seam, and is discarded when `+verifyHostname+` is flipped back to `+true+` (`+:1293-1295+`; tests `+HttpHandlerTest.java:619-730+`). `+javap -p+` confirms the Lombok-generated `+sslContextCallerSupplied(boolean)+` / `+secureSSLContextProvider(...)+` builder setters are `+private+`, so the provenance flag cannot be forged from outside the package.
* *Default hostname verification is proven, not assumed*: `+HttpHandlerHostnameVerificationTest+` connects to a real in-JVM TLS server with a mismatched SAN and asserts rejection, plus a matching-SAN positive control.
* *Redirects*: JDK client stays on `+Redirect.NEVER+` on both constructor paths (`+HttpHandler.java:411-413, 447-452+`; asserted end-to-end `+HttpHandlerIntegrationTest.java:131-169+`). `+https→http+` is refused before the allowlist (`+RedirectPolicy.java:172-176+`, asserted over a real TLS server `+HttpHandlerHttpsIntegrationTest.java:154-188+`). Default is same-origin only; the policy is consulted before the hop counter (`+HttpHandler.java:744-752+`). Probed bypass candidates all refused: scheme-relative `+//evil.example.org/x+`, userinfo trick `+https://api.example.com@evil.example.org/+`, trailing-dot host `+api.example.com.+`; case-different scheme/host and explicit `+:443+` correctly treated as same-origin; IPv6 literals compare correctly. Malformed `+Location+` → typed `+MALFORMED_LOCATION+` with sanitised, length-bounded message (`+:640-679+`). Intermediate and refused hop bodies are drained, never handed to the caller's handler (`+:583-616+`; tests `+HttpHandlerRedirectTest.java:189-257+`). Credentials never reach an `+http+` target even same-origin (`+RedirectPolicy.java:212-214+`; tests `+:608-626+`).
* *Retry*: only `+NETWORK_ERROR+`/`+SERVER_ERROR+` retried (`+HttpErrorCategory.java:92-94+`); non-idempotent methods skipped by default (`+ResilientHttpAdapter.java:410-415+`); exceptional completions re-propagated, never swallowed into `+null+` (`+:463-470+`, test `+ResilientHttpAdapterTest.java:514-540+`); cancellation reaches the in-flight call and the pending backoff (`+:272-288, 344-351+`; tests `+:586-636+` and integration `+:283-318+`); `+*Blocking()+` is interrupt-aware and cancels the request (`+HttpAdapter.java:434-445+`; tests). `+NaN+`/`+±Infinity+` jitter and multiplier are rejected on both construction paths; cap is applied before jitter as documented.
* *ETag adapter*: a 304 with no cache entry is an `+INVALID_CONTENT+` failure, never a fabricated success (`+ETagAwareHttpAdapter.java:1087-1098+`; test `+ETagAwareHttpAdapterIntegrationTest.java:185-205+`); a 304 to POST/PUT/DELETE leaks neither content nor ETag (`+:1074-1085+`; test `+:155-178+`); cache-key delimiters are escaped so header values cannot forge entries (`+:761-772+`; tests `+:700-747+`); an ETag-less or unparseable 200 evicts the superseded entry (`+:945-951+`; tests `+:314-419+`); the cache key is the configured URI, not the terminal hop (`+:1139+`; test `+:770-788+`); caller `+Accept+`/`+Content-Type+` override converter defaults (`+:492-500+`).
* *Result types*: `+HttpResult+` is `+sealed+` with exactly `+Success+`/`+Failure+`, exhaustively switchable (tests `+HttpResultTest.java:321-381+`); `+HttpErrorCategory.fromException+` unwraps nested `+CompletionException+`/`+ExecutionException+` with a self-cause guard (`+:145-149+`); `+HttpStatusFamily.toErrorCategory()+` is complete (1xx/3xx/UNKNOWN → `+INVALID_CONTENT+`, 2xx throws).
* *Log catalogue consistency*: all 13 `+HttpLogMessages+` records (106, 107, 108, 110–117, 200, 201) match `+LogMessages.adoc+` in identifier, level and template text exactly; the overview range line (`+:16+`) is correct.
* *Docs ↔ API signatures* (excluding F-client-6): every other code sample checked (`+HttpHandler+` Javadoc, `+RedirectPolicy+` Javadoc, `+client-handlers-readme.adoc+`, `+http-result-pattern.adoc+`, `+client/package-info.java+` converter/adapter examples) uses methods that exist with the shown signatures (`+tlsVersions(SecureSSLContextProvider)+`, `+RedirectPolicy.builder().maxHops/allowedHosts/credentialForwarding+`, `+HttpResult.Success<T>(var c, var e, var s)+` deconstruction, `+failure.isRetryable()+`, `+StringContentConverter.identity()+`, `+ETagAwareHttpAdapter.statusCodeOnly(handler)+`).
