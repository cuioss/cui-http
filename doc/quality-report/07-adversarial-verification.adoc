== Purpose and outcome

After the six area reports and the lead findings had been consolidated into chapters 01 to 06, an independent verifier with no prior context (a fresh agent that had not seen how the findings were produced) was given the report and the repository with the instruction to break it: re-execute every probe, re-trace every code path, open every cited line, re-check the "verified strengths", check the README numbers, and spend a bounded effort looking for anything material the report had missed. The verifier ran under the same constraints as the review (read-only, probes compiled against `cui-http-core/target/classes`).

.Outcome
* 125 findings checked. 99 confirmed exactly, 22 confirmed with a correction, 2 confirmed on a spot-check basis, 1 confirmed as suspected (F-documentation-23, which the report itself marks SUSPECTED), 1 confirmed and superseded (L-12, superseded by F-client-2), 0 not reproduced, 0 disputed.
* Every High finding was reproduced end to end. F-client-1 was replayed against a MockWebServer with two principals; F-client-3 live against the JDK client; F-client-2, -4 and -11 against the JDK 21u sources.
* 38 "verified strength" claims were re-executed. None was false.
* One new item was found (V-1, now in xref:01-security-validation.adoc[]). Nothing else material was missed in the security core.

.Adjustments made to the report as a result
* Line-number corrections in 20 findings (F-A-9, F-B-12, F-B-14, F-client-1, F-client-9, F-D-1, F-D-2, F-D-15, F-D-17, F-D-19, F-D-20, F-documentation-2, -3, -13, -18, -25, -26 and the redirect strength paragraph in chapter 03). Each corrected location is marked "corrected after adversarial verification" in place.
* Factual corrections: F-client-16 (the quoted builder combination throws rather than builds), F-documentation-7 (the "71 tests" figure is correct), F-documentation-1 (the README does document the Maven wrapper for humans), F-A-3 (the whitespace claim holds for Unicode whitespace only), F-B-14 (the generator uppercases only the dot and slash escapes), F-E-9 (32 generators, not 33), L-1 (paranoid also accepts).
* Severity changes: F-E-1, F-E-2 and F-documentation-2 from High to Medium; F-documentation-1 from Medium to Low; F-documentation-3 from Medium to Low. The report now carries five High findings, all code-side.
* README baseline corrected: the surefire reports hold 112 report files, 206 test classes and 7 874 test cases (0 failures, 0 errors, 0 skipped). The original "336 test classes, 6 993 tests" counted files and summed the per-class text summaries.
* V-1 added as a Medium finding; the duplicates table in chapter 01 and the remediation order in the README reference it.

The verifier's report follows unchanged below (identifiers, line references and severities as it recorded them, before the adjustments above were applied).

Effort spent: ~10 %. Findings:

. **Decoded `+?+`/`+#+` (or invisible characters) glued to a `+..+` segment survive the path pipeline in every preset and the returned value still contains the dot-dot segment.** `+/files/public/..%3F+` → `+/files/public/..?+`; `+/a/b/..%23/c+` → `+/a/b/..#/c+`; `+/a/b/%2e%2e%3f%2fetc%2fpasswd+` → `+/a/b/..?/etc/passwd+` (defaults and strict; paranoid rejects only because of `+/etc/+`). Also `+/a/b/%2e%2e%c2%a0/c+` → `+/a/b/.. /c+` (NBSP) and `+/a/b/..%e2%80%8b/c+` → `+/a/b/..[ZWSP]/c+` (ZWSP). Neither `+PatternMatchingStage+` (needs a separator after `+..+`) nor `+NormalizationStage+` (segment is `+..?+`, not `+..+`) fires, and the decoded `+?+`/`+#+` are not treated as structural. A consumer that reparses the *returned* string as a URL sees path `+/files/public/..+` (`+URI.create("https://h" + out).getPath()+` = `+/files/public/..+`, `+.normalize()+` → `+/files/+`). One level only (the `+?+`/`+#+` terminates the path), so not a root escape.
