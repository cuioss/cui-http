Scope: all 22 AsciiDoc files (`README.adoc`, `cui-http-core/src/site/asciidoc/about.adoc`, and the complete `doc/` tree including `doc/http-security/`), plus `CLAUDE.md` and `agents.md`. Every drift claim was re-verified against the current code.

[NOTE]
====
The documentation suite is *far more accurate than typical* and unusually disciplined about scoping its security claims. Numeric traceability (test counts, line references) checks out almost everywhere, all cross-references resolve, and non-implemented features are usually explicitly flagged. The findings cluster in three places: a handful of residual *overclaims* that contradict the suite's own carefully-scoped statements, *inventory listings* that have drifted behind code changes, and two *navigation gaps*. There are no HIGH-severity findings.
====

== Accuracy / drift

[#DOC-1]
=== DOC-1 (MEDIUM): The Requirements compliance matrix marks standards "✓ Complete" that the traceability matrix marks partial

*Files:* `doc/http-security/Requirements.adoc:101-110` vs `doc/http-security/specification/compliance-traceability.adoc:659-667`.

`Requirements.adoc` shows "OWASP Top 10 2021 … ✓ Complete", "NIST 800-53 … ✓ Complete", "PCI DSS … ✓ Complete". The traceability matrix it links one line below marks OWASP *A09 partial* ("counting only — no logging/alerting/audit"), NIST *AU-2/AU-12 partial*, and PCI *10.2 partial*. The traceability matrix matches the code (`SecurityEventCounter` counts only); the Requirements matrix overstates and risks a false sense of compliance. This is the same "logging is counting only" reality documented honestly elsewhere. *Fix:* align the Requirements matrix with the traceability matrix.

[#DOC-2]
=== DOC-2 (MEDIUM): `owasp-best-practices.adoc` claims a "configurable pattern database" that does not exist

*File:* `doc/http-security/analysis/owasp-best-practices.adoc:195`. This contradicts `security-requirements.adoc` SEC-18, which correctly states runtime-configurable patterns are *not implemented* (`SecurityDefaults.PATH_TRAVERSAL_PATTERNS` etc. are `static final`; the builder exposes only policy toggles, no pattern knob). *Fix:* remove the bullet or mark it as not implemented.

[#DOC-3]
=== DOC-3 (MEDIUM): `owasp-best-practices.adoc` overclaims body validation and contradicts itself

*File:* `doc/http-security/analysis/owasp-best-practices.adoc:253-262`. It says JSON/XML content validation and file-upload filename validation are "Implemented in: URLPathValidationPipeline and URLParameterValidationPipeline", then immediately states "Body validation pipeline has been eliminated … handled at the application layer." The URL pipelines perform no JSON/XML content validation, and `PipelineFactory.createPipeline(BODY, …)` throws. Line 247 also attributes parameter-*name* validation to `URLParameterValidationPipeline`, but names are handled by the separate `URLParameterNameValidationPipeline`. *Fix:* remove the JSON/XML/file-upload claims.

[#DOC-4]
=== DOC-4 (MEDIUM): Two documented forwarded-sanitization config knobs are inert

*File:* `doc/forwarded-header-resolution.adoc:234-240`. The doc says "the full `SecurityConfiguration` surface applies — … `normalizeUnicode`, … and the header allow/block lists". But the resolver sanitizes via `createHeaderValuePipeline` → `HTTPHeaderValidationPipeline` (HEADER_VALUE), whose stages are Length/Character/Normalization(no-op)/Pattern(no-op), with `AllowBlockListStage` added only for HEADER_NAME. There is no `DecodingStage`, and `normalizeUnicode` is consumed *only* by `DecodingStage` (`DecodingStage.java:213`). So `normalizeUnicode`, `allowedHeaderNames`/`blockedHeaderNames`, and `allowDoubleEncoding` have no effect on forwarded-header sanitization. The other listed knobs do apply. *Fix:* list only the knobs that actually affect HEADER_VALUE validation.

[#DOC-5]
=== DOC-5 (MEDIUM): `client-handlers-readme.adoc` claims log levels that do not exist

*File:* `doc/client-handlers-readme.adoc:124-131`. It says `HttpLogMessages` provides "Debug, info, warning, and error levels", but the class contains only `WARN` (HTTP-106–115) and `ERROR` (HTTP-200/201) records — no DEBUG or INFO. *Fix:* correct to WARN/ERROR.

[#DOC-6]
=== DOC-6 (MEDIUM): SEC-3's referenced CVEs appear in no analysis document

*File:* `doc/http-security/security-requirements.adoc:52-60`. SEC-3 lists CVE-2021-41773, CVE-2021-42013, CVE-2020-5410, CVE-2019-0232 with "Reference: xref:analysis/cve-analysis.adoc", but `cve-analysis.adoc` documents a *disjoint* set of 8 CVEs (2024-38819, 2023-50164, 2023-32235, 2022-23457, 2021-44228, 2021-29425, 2020-8908, 2019-11358); none of SEC-3's four appear in any analysis doc (grep: zero hits). CVE-2021-41773 is covered only in test code (`ApacheCVEAttackDatabase`). *Fix:* point the reference at the test database, or add the CVEs to an analysis doc.

[#DOC-7]
=== DOC-7 (LOW): Assorted smaller accuracy gaps

* `doc/http-security/functional-requirements.adoc:33-43` (HTTP-2): "requires only two runtime modules (see `module-info.java`)" — `module-info.java` has three non-static requires (`org.jspecify`, `de.cuioss.java.tools`, `java.net.http`).
* `doc/http-security/specification/specification.adoc` (~line 279): "see the two-pass pattern-matching note *below*" — the note (line 206) is *above*.
* `doc/http-security/README.adoc:69` claims the implementation follows "RFC 8941 – Structured Field Values" — no structured-field code exists (grep: zero hits); its "HTTP Parameter Validation" section cites RFC 7230 for query-parameter-name rules (7230 defines header tokens, not query parameters); and its "Input → Decode → Normalize → Validate → Verify → Output" schematic matches no actual pipeline order (the real path order runs character validation *before* decoding).

== Completeness

[#DOC-8]
=== DOC-8 (MEDIUM): Stale test inventories

The narrative test listings have drifted behind test additions:

* `doc/http-security/specification/testing.adoc:109` — "tests/ … (26)" and the listing omit `ProtocolHandlerAttackDatabaseTest`; the directory has 27. Same stale "26" in `pipeline-architecture-standards.adoc:124`.
* `testing.adoc` shows 4 pipeline test classes; there are 6 (missing `ContentTypeValidationPipelineTest`, `URLParameterNameValidationPipelineBehaviorTest`).
* `compliance-traceability.adoc` Test-Coverage-Summary: "Pipeline Tests: 4" (actual 6), "Validation Stage Tests: 7" (actual 9), "4 legitimate-pattern databases" (only 3 concrete; `LegitimatePatternDatabase` is abstract).
* `doc/test-framework-structure.adoc` is the most stale (see also xref:test-quality-review.adoc#TQ-9[TQ-9]): its database, pipeline, validation-stage, attack, and cookie-generator listings each omit classes that exist.

*Fix:* regenerate these inventories from the tree, or (better) stop hand-maintaining exhaustive counts in prose.

[#DOC-9]
=== DOC-9 (MEDIUM): Orphaned documents and index omissions

* `doc/http-result-pattern.adoc` and `doc/LogMessages.adoc` have zero inbound references from `README.adoc` or any other doc — a reader navigating from the README cannot discover them.
* `doc/http-security/README.adoc`'s Document Index omits `configuration.adoc` (the central enforced-settings reference) and `specification/compliance-traceability.adoc`, even though the README instructs "Update this README index when adding new documents."

*Fix:* link the two orphans from the relevant readmes and add the two missing entries to the index.

[#DOC-10]
=== DOC-10 (MEDIUM): Unimplemented body validation lacks a status note

*File:* `doc/http-security/functional-requirements.adoc:27` (HTTP-1) requires validation of "Request body parameters (form-data, JSON, XML)" with no implementation-status NOTE, while `PipelineFactory:250` throws "BODY validation pipeline has been removed" and `pipeline-architecture-standards.adoc` states the body pipeline was eliminated. The doc set is otherwise diligent about NOTE-ing unimplemented items (HTTP-16/17, SEC-11/12/15/18). Similarly HTTP-14 lists `COOKIE_NAME`/`COOKIE_VALUE`/`BODY` per-type configurations without noting the cookie pipelines throw "not yet implemented" (LOW). *Fix:* add the missing status notes.

[#DOC-11]
=== DOC-11 (LOW): `CLAUDE.md` architecture is a stale subset of the API

`CLAUDE.md` lists only 3 pipelines (omits `URLParameterNameValidationPipeline`, `ContentTypeValidationPipeline`) and 3 client classes (omits the entire `de.cuioss.http.forwarded` package and the `adapter`/`converter`/`result` packages — all exported in `module-info.java`). Because `agents.md` defers to `CLAUDE.md` as "the single source of truth" for architecture, the gap propagates. (`README.adoc` itself does cover forwarded and adapters.) *Fix:* refresh the CLAUDE.md architecture section, or point it at README.

[#DOC-12]
=== DOC-12 (LOW): Pipeline-selection standard omits two pipelines

`doc/http-security/specification/pipeline-architecture-standards.adoc` is billed as "the authoritative standards for selecting appropriate validation pipelines", but its decision matrix treats only `URLPathValidationPipeline` in detail; `URLParameterNameValidationPipeline` and `ContentTypeValidationPipeline` are absent from the "Path vs Content Rule".

== Verified correct / done well

* `doc/LogMessages.adoc` matches `HttpLogMessages`/`ForwardedLogMessages` *exactly* — every ID, template string, and parameter description, including the HTTP-107 untested note.
* `doc/http-security/configuration.adoc` matches `SecurityDefaults`/`SecurityConfigurationBuilder` value-for-value across all three presets (all length limits, encoding flags, count limits, cookie flags, empty allow/block lists).
* Pipeline stage orderings in `specification.adoc` match the constructors exactly, including the six-invocation two-pass path pipeline.
* The scope/limitations discipline is unusually honest and matches code behavior: SEC-5 TOCTOU, the SEC-11/12/15/18 NOTEs, XSS-detection-out-of-scope, the forwarded-resolver trusted-network WARNING, and the TLS-floor "cannot express TLS1.3-only via generic TLS" caveat.
* All code examples spot-checked compile against current signatures (`UrlSecurityException.builder()`, `PipelineFactory.createPipeline`, `RetryConfig` defaults, `HttpResult` factories, `ResilientHttpAdapter.wrap`, `ForwardedResolverConfig` builder, `HttpStatusFamily.isSuccess(int)`).
* *All cross-references resolve*: a check of every relative `xref:`/`link:` target across the 22 files found zero missing files (the sole unresolved link is `about.adoc → index.html`, an expected site-build artifact); all `#anchor` fragments resolve, aided by pre-planted explicit anchors.
* `CLAUDE.md` ↔ `agents.md` duplication is handled well (explicit delegation; the small shared blocks are consistent); `security-readme.adoc` ↔ `http-security/README.adoc` serve distinct roles without contradiction; the TLS-floor text duplicated between `security-readme.adoc` and `client-handlers-readme.adoc` is consistent with the code.
* Requirement traceability was spot-checked on more than ten traces end-to-end (OWASP A01 constants, CWE-22 line references, expanded test counts of 71/213/395/158, the not-implemented annotations, and the "37 = 19 + 18" anchor arithmetic) — all accurate except DOC-6.

== Overall assessment

The doc tree is well-organized (component readmes in `doc/`, a layered spec suite under `doc/http-security/`) and materially more accurate than typical. Fixing the nine MEDIUM items (DOC-1 through DOC-6 and DOC-8 through DOC-10) — the compliance-matrix overclaim, the two `owasp-best-practices` overclaims, the inert forwarded knobs, the phantom log levels, the SEC-3 reference, the stale inventories, the unimplemented-body status note, and the two navigation gaps — would bring the documentation to a very high standard.
