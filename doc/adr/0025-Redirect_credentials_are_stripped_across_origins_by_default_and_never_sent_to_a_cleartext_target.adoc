= ADR-0025: Redirect credentials are stripped across origins by default and never sent to a cleartext target

== Status

Proposed

== Context

This record is written after the fact. It is reconstructed from the code on the branch and from
the commit messages of PR #186 (`9446171`), PR #191 (`384a22c`), PR #194 (`ff12f34`) and PR #240
(`2e9e8e0`). Where those sources state a reason it is reported; where they state none, this record
says so and describes only what the code does.

xref:0024-Redirects_are_followed_by_HttpHandler_behind_a_per-hop_policy_that_is_same-origin_by_default.adoc[ADR-0024]
records that `HttpHandler` follows redirects itself and asks a `RedirectPolicy` whether each hop
may be taken. That answers *where* a request may go. It leaves open *what the request carries*
when a hop is taken: the next request is rebuilt from the previous one, so without a further rule
every header of the original request — including the caller's `Authorization` and `Cookie` — would
travel to whatever target the policy permitted.

Under the default policy that question never arises across origins, because every cross-origin hop
is refused. It arises as soon as a caller allowlists a host: the hop is then followed to a
different origin, chosen by the response of the first one.

PR #186 shipped the answer together with the loop: credential handling on a cross-origin hop is "a
named, public strategy on the same configuration surface", whose "secure default strips
`Authorization`/`Cookie` on any cross-origin hop", while forwarding them to an allowlisted host is
"an explicit caller opt-in, never implicit".

Two later changes refined it:

* PR #191 added a rule above the strategy: a hop whose target scheme is `http` carries neither
  header. The squash commit `384a22c` describes itself as documentation-only with no production
  behaviour change; the change to `RedirectPolicy.forwardsCredentials` and its tests is
  nevertheless part of that commit's diff, and the release-notes summary appended to the same
  message lists it. PR #194 refers to it as the "CWE-319 cleartext guard". No commit reachable
  from this branch carries a message dedicated to the guard.
* PR #240 made `forwardsCredentials` check the allowlist itself "instead of relying on caller
  call-order".

== Decision

=== One method decides, and the follow loop only applies its verdict

`RedirectPolicy.forwardsCredentials(URI from, URI to)` returns whether `Authorization` and
`Cookie` may be carried across the hop. `HttpHandler.rebuildForHop` calls it once per hop and, when
the verdict is `false`, filters both headers (matched case-insensitively) out of the rebuilt
request. `rebuildForHop` holds no origin comparison and no strategy branch of its own.

The method evaluates four steps in order:

. the target scheme is `http`: `false`;
. `from` and the target are same-origin: `true`;
. the strategy is not `FORWARD_TO_ALLOWLISTED`: `false`;
. otherwise: `true` exactly when the target host is in `getAllowedHosts()`.

The verdict never changes what `RedirectPolicy.refuse` decides. A refused hop is not taken, so
nothing is forwarded to it; a permitted hop is taken whether or not the credentials go with it.

=== The strategy is named, and stripping is the default

`RedirectPolicy.CredentialForwarding` has two values:

* `STRIP_ON_CROSS_ORIGIN` — the default of `RedirectPolicy.builder()` and therefore of
  `RedirectPolicy.sameOrigin()`. Both headers are dropped on every hop that is not same-origin. An
  allowlisted host is then reached without them.
* `FORWARD_TO_ALLOWLISTED` — set through
  `RedirectPolicyBuilder.credentialForwarding(...)`. Both headers survive a cross-origin hop, but
  only to a host in `getAllowedHosts()` (step 4).

Step 4 repeats the allowlist test that `refuse` already applied. PR #240 records the reason: the
verdict is then a function of the policy and the two URIs alone, and does not depend on `refuse`
having been called first.

The strategy is configured on the `RedirectPolicy`, next to the allowlist it depends on;
`HttpHandlerBuilder.redirectPolicy(...)` is the only seam, and passing `null` there restores
`STRIP_ON_CROSS_ORIGIN` together with the same-origin default.

=== No strategy reaches a cleartext target

Step 1 runs before the same-origin test and before the strategy, and it cannot be configured: a
hop whose target scheme is `http` carries neither header. Given the rules of `refuse`, exactly two
kinds of hop to an `http` target can be permitted, both starting from a request whose own URI is
`http` — which `HttpHandler.requestBuilder()` produces only for a handler built with
`allowInsecureHttp(true)`:

* an `http` to `http` same-origin hop, under either strategy;
* an `http` to `http` hop to an allowlisted host.

An `https` to `http` hop never reaches `forwardsCredentials`: `refuse` rejects it with
`PROTOCOL_DOWNGRADE`.

The guard withholds the credential and lets the hop proceed; it does not refuse the hop. The
Javadoc of `forwardsCredentials` states the purpose — "no credential is written onto an unencrypted
wire" — and PR #194 labels the rule with CWE-319 (cleartext transmission of sensitive information).
Beyond that the rationale is not on record: no source says why the hop is taken without credentials
rather than refused, or why the rule also covers the same-origin `http` hop, whose origin already
received the same credential in cleartext on the request that produced the redirect.

=== The credential is these two headers

The filter in `rebuildForHop` names `Authorization` and `Cookie` and nothing else. Every other
header of the request and — on a `307` or `308`, which replay the method and body — the request
body are carried to the next hop unchanged. The rationale for
limiting the set to these two headers is not on record.

== Consequences

=== Positive

* Allowlisting a host for redirects does not by itself hand that host the caller's credentials.
  Forwarding takes a second, separately named opt-in.
* The rule is one pure method. `RedirectPolicyTest` covers it directly, and it gives the same
  answer in whichever order `refuse` and `forwardsCredentials` are called.
* On a redirect hop, neither header is sent over `http`, whatever the policy says.
* A credential stripped on one hop does not come back later in the chain: each hop is rebuilt from
  the request of the hop before it, not from the caller's original request.

=== Negative

* A hop that is followed without credentials is not reported by the client. The caller receives
  whatever the target answers to the request without them, and nothing in that response says the
  headers were withheld.
* On a cleartext handler, a same-origin redirect now arrives unauthenticated at an origin that
  received the credential on the first request. The guard removes the header from the hop; it
  cannot take back the first transmission.
* `FORWARD_TO_ALLOWLISTED` is all-or-nothing across the allowlist: every allowlisted host receives
  both headers. The policy cannot forward to one allowlisted host and strip for another.

=== Risks

* The guard covers redirect hops only. The first request of a handler built with
  `allowInsecureHttp(true)` is sent exactly as the caller built it, including any `Authorization`
  or `Cookie`. Wording that reads as "a cleartext handler cannot leak a credential" overstates the
  rule.
* The set of headers treated as credentials differs between two parts of the client.
  `ETagAwareHttpAdapter` binds a cache entry to `Authorization`, `Cookie` and
  `Proxy-Authorization`
  (xref:0023-A_cache_entry_is_bound_to_the_credential_material_that_produced_it.adoc[ADR-0023]);
  the redirect filter strips the first two only. A `Proxy-Authorization` header, or an API key in
  a custom header, crosses an origin boundary on a permitted hop.
* The adapter computes its cache key from the caller's request before the handler follows any hop,
  and stores the terminal response of the chain under it. An entry bound to a principal under
  ADR-0023 can therefore hold a representation that was fetched on a hop from which that
  principal's credentials had been stripped.
* The executable guards are `RedirectPolicyTest` (strategy, allowlist re-check and the cleartext
  cases, with an `https` positive control), `HttpHandlerRedirectTest` (cleartext hops over the
  wire) and `HttpHandlerHttpsIntegrationTest` (`sameOriginHopOverTlsKeepsCredentials`,
  `forwardToAllowlistedCrossOriginHopOverTlsKeepsCredentials`,
  `stripOnCrossOriginHopOverTlsDropsCredentials`). PR #194 added the last two because the cleartext
  guard had turned the only earlier end-to-end proof of forwarding into a strip case.

== Alternatives Considered

The first two are alternatives the record addresses. The remaining ones are alternatives the code
visibly did not take and for which no reason is recorded.

* **Forward credentials to every host the policy permits.** This is what rebuilding the request
  without a filter would do. PR #186 rejects it: forwarding to an allowlisted host is "an explicit
  caller opt-in, never implicit".
* **Leave the allowlist test to the earlier `refuse` call.** This was the first implementation:
  under `FORWARD_TO_ALLOWLISTED` the method returned `true` for any cross-origin hop and was
  documented as meaningful only for a hop `refuse` had already permitted. PR #240 replaced it
  because the verdict then depended on the order in which a caller invoked the two methods.
* **Never forward across origins.** The code offers `FORWARD_TO_ALLOWLISTED` instead. The rationale
  for offering the opt-in is not on record.
* **Refuse a hop to an `http` target outright instead of stripping.** Not taken; `refuse` still
  permits both `http` to `http` cases. The rationale is not on record.
* **Make the cleartext rule a third strategy value or a builder flag.** Not taken; the rule is
  unconditional. The rationale is not on record beyond the stated purpose of keeping credentials
  off an unencrypted wire.
* **A configurable or wider set of credential headers.** Not taken; the two header names are
  constants in `HttpHandler`. The rationale is not on record.
