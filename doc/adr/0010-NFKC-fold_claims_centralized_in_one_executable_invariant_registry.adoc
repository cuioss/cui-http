== Status

Accepted

== Context

The security test tree contains code that reasons about Unicode normalization-based evasion: a payload substitutes a visually similar or NFKC-foldable code point for an ASCII delimiter, hoping the substitution survives decoding and later folds back into the delimiter's meaning. Comments and Javadoc throughout the test and generator sources assert which specific code points fold to which ASCII targets under NFKC, to explain why a given payload is a real attack instance.

These fold claims live only in prose. Nothing executes them. A claim can be wrong — a code point genuinely normalizes to itself rather than folding to the delimiter the comment describes — and the surrounding test still passes, because the test's actual assertion is about the pipeline's rejection of the payload, not about the normalization property the comment uses to justify it. This defect class recurred across separate, independent changes: the same kind of false fold claim was introduced, and each fix corrected only the specific instance found, without closing the underlying gap that no test runs the codepoints' actual normalization behavior.

A prior attempt at executable verification existed but was local and partial: one generator's own test class asserted NFKC folding for its private set of code points, and separately mentioned two non-folding code points by name only inside a failure-message string — a claim inside prose text, not an assertion the test framework evaluates.

== Decision

Every normalization-fold claim made anywhere in the module's sources — in a comment, in Javadoc, or in an existing test, in `src/main/java` as well as `src/test/java` — is represented as a row in one structured claims table, `CLAIMS`, inside one shared invariant test. A row names an input (usually one code point, or a base character plus combining marks for a composition claim), the normalization form the claim is about (NFKC, or NFC where a comment makes an NFC claim), and either its claimed result or the negative claim that it normalizes to itself. Each row records the source of the claim (the file and construct it came from), so a failure traces directly back to the comment or Javadoc it is verifying.

Every assertion is derived from that one table: the positive rows assert `Normalizer.normalize(input, form)` equals the claimed result and differs from the input, the negative rows assert the input normalizes to itself. There is no second, hand-maintained list of what to assert.

Completeness of the table is **enforced, not trusted**. The same test scans every Java source in the module for fold-claim contexts — a comment paragraph or code line that mentions folding or a normalization form together with a code point written as `U+XXXX` or as a Java unicode escape — and fails when such a context names a code point that no row of the table covers (as part of a row's input or claimed result). A fold claim therefore cannot be written in a comment or Javadoc without a row asserting it: the build fails until the row is added or the comment is corrected. The detection is deliberately broad — a code point merely mentioned next to a fold claim must be registered too, which costs one row, whereas a missed claim is the defect this decision exists to prevent.

No second, parallel fold-verification mechanism is kept alongside the shared registry. Where a local, per-class fold assertion already existed, its claims are absorbed into the shared registry as rows and the local assertion is removed — the registry is the single executable source of truth for what folds to what in this module's sources, in both directions.

== Consequences

=== Positive

* A false or drifted fold claim fails a test rather than shipping silently, closing the recurrence path that let the same defect class through multiple times.
* Every claim's provenance is recorded in one place, so verifying "does this comment's fold claim still hold" is a single registry lookup rather than a tree-wide prose search.
* Negative claims (a code point that does *not* fold) are asserted the same way positive claims are, so a "this looks confusable but does not normalize" comment carries the same executable weight as a "this folds" comment.

=== Negative

* Centralizing the registry couples every fold-claiming file to one shared test class for verification purposes; a change to how a claim is phrased in its origin file does not itself update the registry row's claimed result, so the two must be kept in sync by the author making the change.
* The source scan is broad by design, so a comment that merely mentions a code point next to a normalization term forces a row even when it makes no fold claim about that code point.

=== Risks

* The source scan recognizes a claim by its shape — a normalization or fold term plus a code point spelled `U+XXXX` or as a unicode escape, within one comment paragraph or code line. A claim that names its code point only by character name, or splits the code point and the fold term across paragraphs, is not detected. The scan checks that a claimed code point is registered, not that the comment's stated target matches the row's.

== Alternatives Considered

Fix each false fold-claim comment where it is found, without adding a structural test:: Rejected. This is exactly the fix each of the prior escapes already applied. It closes the individual instance and leaves the general gap — that no test runs any codepoint's actual normalization behavior — open for the next payload authored with a plausible-sounding but wrong fold claim.

Keep a fold assertion local to each generator's own test class, one mechanism per class:: Rejected. Produces multiple duplicated, parallel fold-verification mechanisms scattered across the tree instead of one; a local, positive-only assertion also has nowhere natural to place a negative claim, so a "does not fold" statement stays confined to prose (a failure-message string) even when the surrounding positive claims are executable.

Add an inline fold assertion directly at each individual test method that relies on a folding code point:: Rejected. Duplicates the same code-point-to-target mapping across every call site that happens to use it, with no single place recording which code points are known to fold to what, and no natural home for the negative (self-normalizing) rows at all.
