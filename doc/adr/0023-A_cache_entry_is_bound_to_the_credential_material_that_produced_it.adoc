= ADR-0023: A cache entry is bound to the credential material that produced it

:toclevels: 2

== Status

Proposed

== Context

`ETagAwareHttpAdapter` caches a representation under a key derived from the request URI and a
caller-configured subset of the request headers. Which headers enter the key is chosen by a
`CacheKeyHeaderFilter`, and the documented configuration for a client whose token is refreshed
periodically is `excluding("Authorization")` — keeping the rotating credential out of the key so a
refresh does not fragment the cache into one entry per token.

That filter was doing two jobs at once, and only one of them was intended. Keeping a *rotating*
credential out of the key is a bandwidth choice about one principal. But the same exclusion also
made two *different* principals collapse onto one key: caller B, presenting its own credential,
resolved caller A's entry. Two consequences followed from that single collapse. B could revalidate
against A's validator and be served A's representation; and when the origin answered B's request
with a `403`, the adapter's graceful-degradation path surfaced A's cached body as fallback content —
handing back a representation past the very check that had just rejected the caller.

The cached-fallback rule had a second problem independent of the key. Fallback content existed to
bridge an *availability* failure: the server could not serve the representation right now, so stale
content is better than nothing. It was applied to every error status. A `4xx` is not an availability
statement — it says something about *this* request (the caller may no longer read the resource, it is
gone, the request is malformed) — so answering one with cached content contradicts what the server
said.

Separately, the client's error taxonomy had no way to say "the caller asked us to stop".
`HttpErrorCategory.fromException` classified an `InterruptedException` as `CONFIGURATION_ERROR`,
because it is not an `IOException` and everything else fell through to that bucket. Two things went
wrong at once: a cancellation was reported as a misconfiguration, and the interrupt flag the throw
had cleared was never restored, so callers further up the stack could not observe the cancellation
at all.

Finally, `HttpResult.Success` accepted any `int` status. Its factory Javadoc said "typically 200 or
304", and "typically" is what let the contract drift: nothing prevented a redirect or an error status
from being wrapped in a value whose `isSuccess()` returns `true`.

== Decision

=== The cache key binds to the principal, unconditionally

Every cache key carries a trailing principal term derived from the request's credential-bearing
headers, computed **independently of the configured `CacheKeyHeaderFilter`**. The filter decides
which headers are reproduced verbatim in the key; it never decides whether two different principals
share an entry.

No credential value is retained verbatim. Credential material is reduced to its SHA-256 digest both
in the header section and in the principal term, so a key that lives as long as its entry does not
hold the credential that produced it. The digest separates principals exactly as the raw value
would. A request presenting no credential binds to a stable anonymous term rather than to the empty
string, keeping anonymous entries in a namespace of their own.

Cache entries additionally carry a time-to-live alongside the existing size-triggered eviction. An
entry at or past its TTL is treated as absent: neither served as fallback content nor offered as an
`If-None-Match` validator.

=== Cached fallback is restricted to availability failures

An error response surfaces cached content and the cached ETag only when the failure is one of
availability: a `GET` holding a cache entry that was answered with a `5xx`. Every `4xx` yields a
failure whose `fallbackContent` and cached ETag are both `null`.

=== Interruption is a first-class, non-retryable category

`HttpErrorCategory` gains a sixth member, `INTERRUPTED_ERROR`. `fromException` classifies an
`InterruptedException` to it ahead of every other test — including the `IOException` test — reached
either directly or through the existing `CompletionException` / `ExecutionException` unwrap loop, and
calls `Thread.currentThread().interrupt()` before returning so the cancellation stays observable.
The member is deliberately **not** retryable: retrying would ignore the very cancellation that was
asked for. `isRetryable()` is unchanged, since it already tests for `NETWORK_ERROR` and
`SERVER_ERROR` alone.

=== A success carries a 2xx or 304 status

`HttpResult.Success`'s compact constructor rejects any status that is neither in `200..299` nor
exactly `304`, with an `IllegalArgumentException`. The predicate is the whole 2xx range and not a
literal 200-or-304 pair: the production construction site guards on `HttpStatusFamily.isSuccess`, so
`201`, `204`, `205` and `206` are all legitimate. `HttpResult.Failure`'s compact constructor rejects a
`null` `errorMessage` or `category`, both of which are mandatory to the accessors built on them.

== Consequences

=== Positive

* A consumer using the documented `excluding("Authorization")` filter keeps its bandwidth benefit —
  one principal's rotating token still resolves to one entry — while two different principals can no
  longer read each other's representations, through either the revalidation path or the fallback
  path.
* A credential no longer appears verbatim in any string the adapter retains.
* An entry can no longer answer indefinitely: the TTL bounds how long, which the size-triggered
  eviction never did.
* Interruption is reported as interruption, and the restored flag lets callers up the stack act on a
  cancellation instead of discovering a spurious configuration error.
* A `Success` value can no longer disagree with what the server said, so `isSuccess()` is meaningful
  without a second status check at every call site.

=== Negative

* **Breaking: `HttpErrorCategory` gains a member.** The published enum goes from five members to six.
  An exhaustive `switch` over the enum in consuming code no longer compiles until an
  `INTERRUPTED_ERROR` arm is added, and any code asserting a member count or an exact member set will
  fail. This is intentional and is the reason the change is recorded here.
* A cache warmed by one principal no longer serves another. Where two callers previously shared an
  entry by accident, each now performs its own origin fetch — more requests, in exchange for the
  isolation.
* A caller that relied on a `4xx` surfacing cached content for graceful degradation no longer
  receives it. Degrading onto stale content on a `403` or a `404` was never a supported guarantee;
  the `5xx` path remains.
* Constructing a `Success` with a redirect or error status now throws where it previously produced a
  value. A caller doing so was building a result that contradicted its own `isSuccess()`.

=== Integrator-visible behaviour changes landed alongside this decision

* **Cached fallback (deliverable 1).** A `4xx` carries neither fallback content nor a cached ETag; a
  `5xx` on a `GET` holding an entry still does.
* **Redirect method rewrite (deliverable 6).** The `301`/`302` method rewrite is narrowed to `POST`.
  A `PUT`, `PATCH` or `DELETE` that is redirected keeps its method instead of arriving as a `GET`,
  which is what RFC 7231 permits and what a caller expects.
* **Retry delay floor (deliverable 9).** `RetryConfig` requires a delay of at least one millisecond.
  A sub-millisecond value is rejected at configuration time rather than degenerating into a busy
  retry loop.
* **Result-type invariants (deliverable 10).** The 2xx-or-304 success-status invariant and the
  `Failure` null rejections above, plus the new `INTERRUPTED_ERROR` member.

=== Risks

* A future filter, or a new credential-bearing header, could reintroduce the collapse if the
  principal term stopped being computed unconditionally. The guard is executable:
  `ETagAwareHttpAdapterTest` pins both halves — a second principal performs its own origin fetch and
  never receives the first principal's validator, and the same principal still revalidates against
  its own entry, which is the control that keeps the rule from degrading into "never cache".
* The `4xx`/`5xx` split is a status-class rule, so a future status added to the wrong branch would
  reopen the fallback path. The `503` positive control alongside the `401`/`403`/`404` cases is what
  keeps the narrowing attributable to the status class rather than to a blanket removal.

== Alternatives Considered

* **Make the principal binding depend on the configured filter.** The filter could have been read as
  the caller's declaration of what identifies a request, binding only when it admits the credential.
  Rejected: that is exactly the status quo that produced the collapse. The documented
  `excluding("Authorization")` configuration is the one a caller is most likely to choose, and it is
  the one under which isolation would then be absent.
* **Store the credential verbatim in the key.** Simpler, and it separates principals correctly.
  Rejected: the key outlives the request inside the cache map, so this retains the credential for the
  lifetime of the entry to no benefit the digest does not already provide.
* **Drop cached fallback entirely.** This would close the cross-principal leak without any status
  reasoning. Rejected: it also deletes the graceful degradation the fallback exists for, which is
  legitimate and unaffected by the leak once entries are bound to their principal.
* **Classify `InterruptedException` as `NETWORK_ERROR`.** It would at least stop reporting a
  cancellation as a misconfiguration. Rejected: `NETWORK_ERROR` is retryable, so the adapter would
  retry a request the caller had just asked it to abandon.
* **Add `INTERRUPTED_ERROR` without the breaking enum change, e.g. by reusing an existing member.**
  Rejected: every existing member either mis-describes interruption or makes it retryable. The plan's
  compatibility setting is `breaking`, and the member set is the honest place for the distinction.
