== Overview

This document defines the security-specific requirements for the HTTP Security Validation system. These requirements ensure the system effectively prevents, detects, and mitigates security vulnerabilities in HTTP input processing, with emphasis on OWASP Top 10 compliance and CVE prevention.

These requirements are derived from:

* xref:analysis/owasp-best-practices.adoc[OWASP Security Best Practices]
* xref:analysis/cve-analysis.adoc[CVE Analysis and Lessons Learned]
* xref:specification/specification.adoc[Architecture Specification]

== OWASP Compliance Requirements

[#SEC-1]
=== SEC-1: A03:2021 Injection Prevention

* The system must reject the HTTP-component input it validates when that input carries characters
  outside the component's RFC character set, an unsafe encoding, or a path traversal
* Must validate and canonicalize all input before it is handed downstream; invalid input is
  rejected, never repaired
* Must combine two complementary layers:
  ** Positive validation: `CharacterValidationStage` admits only the RFC character set of the
     validated component (RFC 3986 path and query characters, RFC 7230 token and field-value
     characters, RFC 6265 `cookie-octet`) and rejects every other character
  ** Negative validation: `PatternMatchingStage` is block-list based — it rejects input that
     matches a known attack pattern: path traversal (unconditional), a leading protocol-handler
     scheme (when `failOnSuspiciousPatterns` is set) and the sensitive-path and parameter-name
     block-lists (when they are non-empty). This layer covers URL paths and parameter names and
     values only; header, content-type and cookie input relies on the positive layer (plus the
     length, allow/block-list and cookie-prefix rules)
* Must prevent:
  ** Path injection/traversal

* NOTE: Generic injection protection for downstream sinks is *not implemented*. No stage checks a
  value against the grammar of the interpreter it will eventually reach, so a value that passes
  validation can still be dangerous in a shell command, an SQL statement, an LDAP filter, an HTML
  page or a filesystem call. Sink-specific encoding, escaping or parameterization remains the
  caller's responsibility:
  ** Command injection (including via file paths) — NOT IMPLEMENTED (caller responsibility)
  ** SQL, LDAP, XPath and other interpreter injection — NOT IMPLEMENTED (caller responsibility)
  ** Cross-site scripting / output-context injection — NOT IMPLEMENTED (caller responsibility, see
     xref:#SEC-2[SEC-2])
* NOTE: Pattern matching is *not* allow-list based. There is no positive grammar of permitted
  paths or parameter values beyond the per-component character sets above; anything that passes
  the character allow-list and matches no block-listed pattern is accepted.
* Reference: xref:analysis/owasp-best-practices.adoc#_a032021_injection[OWASP A03:2021]

[#SEC-2]
=== SEC-2: A04:2021 Insecure Design

* The system must implement defense in depth
* Must use multiple validation layers:
  ** Input validation (length, character set and attack-pattern stages)
  ** Canonicalization (percent-decoding and Unicode normalization in `DecodingStage`, RFC 3986
     dot-segment resolution in `NormalizationStage`)

* NOTE: Output encoding and access-control verification are *not implemented*. The library
  validates inbound HTTP components only; it never renders output and has no notion of a
  principal or a protected resource. Both remain the caller's responsibility:
  ** Output encoding — NOT IMPLEMENTED (caller responsibility)
  ** Access-control verification — NOT IMPLEMENTED (caller responsibility)
* Must fail securely (deny by default)
* Must implement secure defaults for all configurations
* Reference: xref:specification/specification.adoc#_architecture[Architecture]

== Path Traversal Security Requirements

[#SEC-3]
=== SEC-3: Traversal Pattern Detection

* The system must detect all known path traversal patterns
* Must detect patterns from CVE database including:
  ** link:https://nvd.nist.gov/vuln/detail/CVE-2021-41773[CVE-2021-41773]: Apache httpd path traversal — encoded in link:../../cui-http-core/src/test/java/de/cuioss/http/security/database/ApacheCVEAttackDatabase.java[ApacheCVEAttackDatabase]
  ** link:https://nvd.nist.gov/vuln/detail/CVE-2021-42013[CVE-2021-42013]: Apache httpd double encoding — encoded in link:../../cui-http-core/src/test/java/de/cuioss/http/security/database/ApacheCVEAttackDatabase.java[ApacheCVEAttackDatabase]
  ** link:https://nvd.nist.gov/vuln/detail/CVE-2020-5410[CVE-2020-5410]: Spring Cloud Config traversal — cited as a representative traversal class; not individually encoded in the attack databases
  ** link:https://nvd.nist.gov/vuln/detail/CVE-2019-0232[CVE-2019-0232]: Apache Tomcat RCE via traversal — cited as a representative traversal class; not individually encoded in the attack databases

* Must detect novel combinations of known techniques
* Must maintain pattern database for emerging threats
* Reference: link:../../cui-http-core/src/test/java/de/cuioss/http/security/database/[Attack Databases]. The four CVEs above are *not* covered by xref:analysis/cve-analysis.adoc[CVE Analysis], which analyses a different CVE set.

[#SEC-4]
=== SEC-4: HTTP Protocol Encoding Attack Prevention

* The system must prevent all HTTP protocol-layer encoding-based bypass attempts
* Must handle:
  ** Single URL encoding (`%2e%2e%2f`)
  ** Double URL encoding (`%252e%252e%252f`)
  ** UTF-8 overlong encoding attacks
  ** Mixed case hexadecimal encoding
  ** Unicode normalization attacks

* **ARCHITECTURAL BOUNDARY**: HTML entity encoding and Base64 decoding are application-layer responsibilities
* Must validate at HTTP protocol decoding stage only
* Reference: xref:specification/specification.adoc#_validation_stages[Validation Stages]

[#SEC-5]
=== SEC-5: Canonicalization Security

* The system must safely canonicalize the URL/path *string* (RFC 3986 dot-segment resolution
  and Unicode canonicalization) before pattern matching
* NOTE: Filesystem-level canonicalization is *out of scope and not implementable* in a
  string-based HTTP-component validator. The following are the responsibility of the
  application / filesystem layer and are *not* handled here:
  ** Symbolic links
  ** Hard links
  ** Junction points (Windows)
  ** UNC paths
  ** TOCTOU (Time-of-Check-Time-of-Use) resolution — requires filesystem access, not string input
* Reference: xref:specification/specification.adoc#_validation_stages[Validation Stages]

== Input Validation Security Requirements

[#SEC-6]
=== SEC-6: Strict Input Validation

* The system must enforce strict input validation rules
* Must reject any input that doesn't match expected patterns
* Must validate:
  ** Length constraints (prevent buffer overflows)
  ** Character sets (reject characters outside the component's RFC character set; this is not
     sink-specific injection protection, see xref:#SEC-1[SEC-1])
  ** Format patterns (ensure structure)

* NOTE: Semantic validity (business-logic rules) is *not implemented*. The library has no
  knowledge of what a valid value means to the application, so semantic validation remains the
  caller's responsibility.
* Must not attempt to "fix" invalid input
* Reference: xref:specification/specification.adoc#_validation_stages[Validation Stages]

[#SEC-7]
=== SEC-7: Null Byte and Control Character Prevention

* The system must block all null bytes and control characters
* Must detect:
  ** Raw null bytes (`\0`)
  ** Encoded null bytes (`%00`, `\u0000`)
  ** Control characters (0x00-0x1F, 0x7F)
  ** Unicode control characters

* Must prevent null byte injection attacks
* Must prevent log injection via control characters
* Reference: xref:specification/specification.adoc#_validation_stages[Validation Stages]

[#SEC-8]
=== SEC-8: Unicode and Internationalization Security

* The system must handle Unicode securely
* Must prevent:
  ** Homograph attacks (visual spoofing)
  ** Normalization vulnerabilities
  ** Bidirectional text attacks
  ** Zero-width character abuse
  ** Case transformation attacks

* Must canonicalize Unicode in `DecodingStage` using NFKC for URL paths and NFC for
  parameter values (normalize-and-continue per the OWASP canonicalize-then-validate model)
* Must detect when a fold introduces a structurally significant separator character
* Reference: xref:specification/specification.adoc#_validation_stages[Validation Stages]

== Denial of Service Prevention Requirements

[#SEC-9]
=== SEC-9: Resource Exhaustion Prevention

* The system must prevent resource exhaustion attacks
* Must enforce limits on input length (prevent memory exhaustion): `LengthValidationStage`
  enforces the per-component limits configured on `SecurityConfiguration`, and
  `RequestCollectionValidator` enforces the parameter, header and cookie count limits
* NOTE: The following limits are *not implemented*. No stage measures elapsed time, counts
  decoding iterations or budgets regular-expression evaluation; `DecodingStage` performs a single
  percent-decoding pass followed by a strict UTF-8 decode, so there is no iteration to bound:
  ** Processing-time limits — NOT IMPLEMENTED
  ** Decoding-iteration limits — NOT IMPLEMENTED
  ** ReDoS / regex-complexity budgets — NOT IMPLEMENTED
* Must fail fast when the input-length limits are exceeded
* Reference: xref:specification/specification.adoc#_validation_stages[Validation Stages]

[#SEC-10]
=== SEC-10: Algorithmic Complexity Protection

* The system must use algorithms with predictable complexity
* Must avoid:
  ** Exponential algorithms
  ** Unbounded recursion
  ** Catastrophic backtracking in regex

* Must use linear or logarithmic algorithms where possible
* NOTE: Circuit breakers for long-running operations are *not implemented*. No stage tracks or
  interrupts its own running time; bounding the work per request relies on the input-length
  limits of xref:#SEC-9[SEC-9].
* Reference: xref:specification/testing.adoc#_performance_validation[Performance Security]

== Security Monitoring Requirements

[#SEC-11]
=== SEC-11: Security Event Counting

* The system counts security events via `SecurityEventCounter` (in-memory, per-failure-type
  atomic counters). Detected violations are also surfaced as `UrlSecurityException`.
* NOTE: The validation core does *not* log security events itself and does *not* provide
  built-in SIEM integration. Logging (with context redaction) is performed by the caller at
  the trust boundary where the exception is caught. The following are therefore *not
  implemented* inside `de.cuioss.http.security`:
  ** Structured event logging
  ** Threshold-violation logging
  ** SIEM shipping
* Reference: xref:specification/specification.adoc#_security_event_tracking[Security Event Tracking]

[#SEC-12]
=== SEC-12: Attack Pattern Recognition

* The system recognizes individual attack patterns per request (`PatternMatchingStage`)
* Which patterns a given preset enforces is governed by the tiering rule in
  xref:../adr/0015-A_pattern_literal_enforced_by_a_named_preset_must_be_decidable_from_the_HTTP_component_alone.adoc[ADR-0015]:
  path traversal is unconditional, the protocol-handler scheme check is gated on
  `failOnSuspiciousPatterns`, and the application-layer content judgement is reachable only via
  `paranoid()` or an explicit block-list.
* NOTE: Cross-request correlation and active response are *not implemented*.
  `SecurityEventCounter` provides raw per-failure-type counts only; the library performs
  *no* rate limiting, blocking, or alerting. The following are therefore the caller's
  responsibility and are *not* provided:
  ** Repeated-failure / brute-force detection
  ** Automated-tool signature correlation
  ** Rate limiting and blocking
  ** Alert generation
* Reference: xref:specification/specification.adoc#_security_event_tracking[Security Event Tracking]

== Cryptographic and Encoding Requirements

[#SEC-13]
=== SEC-13: Secure Encoding Handling

* The system must handle encoding securely
* Must:
  ** Handle encoding errors safely
  ** Validate encoding consistency

* Must not leak information through error messages
* NOTE: Constant-time comparison is *not implemented*. There is no `MessageDigest.isEqual` or
  equivalent anywhere in `de.cuioss.http.security`; the validation stages compare with ordinary
  `String` and `Set` operations whose runtime depends on the input. Timing-side-channel
  resistance is therefore *not* a property this library provides. The following are
  consequently *not implemented*:
  ** Constant-time comparison
  ** Timing-attack prevention
* Reference: xref:specification/specification.adoc#_validation_stages[Validation Stages]

[#SEC-14]
=== SEC-14: Secure Defaults

* The system must use secure defaults for all security settings
* The shipped default (`SecurityConfiguration.defaults()`, the *balanced* preset) includes:
  ** Null bytes and control characters blocked
  ** Extended ASCII blocked (`allowExtendedAscii=false`)
  ** Double encoding rejected and Unicode normalization enabled
  ** Conservative length and count limits taken from `SecurityDefaults`
  ** The RFC character set of each validated component as its allow-list
  ** Path-traversal detection active; the protocol-handler scheme check is *off*
     (`failOnSuspiciousPatterns=false`) and the content block-lists are empty

* The default is not the maximum-security posture: `strict()` enables the protocol-handler scheme
  check but keeps the content block-lists empty, and only `paranoid()` (or a caller-supplied
  block-list) enables the application-layer content detection (see the NOTE below)
* Configuration relaxation must require explicit action
* Reference: xref:specification/specification.adoc#_configuration_architecture[Secure Configuration]

[NOTE]
====
The shipped out-of-the-box default (`SecurityConfiguration.defaults()`, identical to
`builder().build()`) is the *balanced* preset: it is secure by default and requires an explicit,
opt-in change to relax, but it is not the maximum-security preset (for example it ships
`failOnSuspiciousPatterns=false`). `SecurityConfiguration.strict()` is the *recommended production
posture*: it turns on the structural checks — including the protocol-handler scheme detection — and
accepts a realistic REST API vocabulary. `SecurityConfiguration.paranoid()` is the
*maximum-security* posture: it is `strict()` plus the application-layer content detection, seeding
`blockedPathPatterns` and `blockedParameterNames` from `SecurityDefaults`. That extra detection
carries a real false-positive cost — it rejects paths whose segments are ordinary API vocabulary
such as `root`, `dev` or `etc`, and parameter names such as `file` or `url` — so choose it only
where URL paths and parameters really do reach a filesystem, or seed a narrower block-list of your
own on any base preset via `SecurityConfiguration.withContentBlockLists(Set, Set)`. See
xref:specification/specification.adoc#_default_security_posture[Default Security Posture] and
xref:configuration.adoc[Configuration Reference] for the exact per-preset values.
====

== Compliance and Audit Requirements

[#SEC-15]
=== SEC-15: Audit Trail Support

* Each violation carries audit-relevant context on the thrown `UrlSecurityException`
  (failure type, validation type, original input, sanitized input, detail message), and is
  counted by `SecurityEventCounter`.
* NOTE: A persistent, tamper-evident audit trail is *not implemented*. `SecurityEventCounter`
  holds only in-memory, resettable counts; it does not persist records, sign them, or
  integrate with enterprise audit systems. Durable, tamper-evident audit logging is the
  caller's responsibility.
* Reference: xref:specification/specification.adoc#_security_event_tracking[Security Event Tracking]

[#SEC-16]
=== SEC-16: Security Testing Support

* The system must support security testing
* Must provide:
  ** Test data generators for security patterns, published as the `generators` classifier
     artifact so that automated (JUnit-based) security tests in consuming projects can reuse them
  ** Security regression test support (the attack databases and the tests that replay them)

* NOTE: The following are *not implemented*. The library ships no instrumentation or extension
  point aimed at penetration-testing tooling, and no coverage figure is tracked separately for
  the security tests — code coverage is measured for the module as a whole by the build's
  `coverage` profile:
  ** Penetration testing hooks — NOT IMPLEMENTED
  ** Security-specific test coverage metrics — NOT IMPLEMENTED
* Reference: xref:specification/testing.adoc[Security Testing Framework]

== Third-Party Integration Security

[#SEC-17]
=== SEC-17: API Security

* The system must provide a secure API
* Must:
  ** Use immutable objects where possible
  ** Prevent API misuse through design
  ** Validate all API inputs
  ** Document security considerations

* Must follow secure coding practices
* Reference: xref:specification/specification.adoc#_core_components[Core Components]

== Security Update Requirements

[#SEC-18]
=== SEC-18: Attack Pattern Configuration

* The attack-pattern set is *partly* configurable. The sensitive-path and parameter-name
  block-lists ARE caller-supplied: `SecurityConfiguration.blockedPathPatterns()` and
  `blockedParameterNames()` accept any set, and `SecurityDefaults.SENSITIVE_PATH_PATTERNS` /
  `SUSPICIOUS_PARAMETER_NAMES` are only the reference values `paranoid()` happens to seed them
  with.
* NOTE: The remaining pattern sets are *not* runtime-configurable. `PATH_TRAVERSAL_PATTERNS`, the
  encoded-traversal regexes and `PROTOCOL_HANDLER_SCHEMES` are `static final` compile-time
  constants with no configuration knob, so changing them requires a code change and a new release.
  This is deliberate: they encode structural violations that hold independently of any
  application's sink (see
  xref:../adr/0015-A_pattern_literal_enforced_by_a_named_preset_must_be_decidable_from_the_HTTP_component_alone.adoc[ADR-0015]).
* `SecurityConfiguration` additionally exposes configurable *policy* toggles (length limits,
  encoding/character policy, header-name and content-type allow/block lists).
* Reference: xref:analysis/cve-analysis.adoc[Attack Pattern Analysis]
