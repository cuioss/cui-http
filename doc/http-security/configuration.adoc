= HTTP Security Configuration Reference
:toc: macro
:toclevels: 3

This document is the central reference for every *enforced* setting in
`de.cuioss.http.security.config.SecurityConfiguration`. For each knob it lists the default
value across the four presets and the stage / validator that enforces it.

Every setting listed here is enforced. Single-value settings are consumed by the validation
stages inside the pipelines built by `PipelineFactory`; request-level settings that need
collection or attribute context are enforced by dedicated validators
(`RequestCollectionValidator`, `CookiePrefixValidationStage`).

toc::[]

== Presets

Four presets are provided as the single source of truth
(`de.cuioss.http.security.config.SecurityDefaults`), ordered from most permissive to most
restrictive:

* `SecurityConfiguration.lenient()` — maximum compatibility (trusted environments only)
* `SecurityConfiguration.defaults()` — balanced (identical to `builder().build()`)
* `SecurityConfiguration.strict()` — security over compatibility; the recommended hardened
  production posture
* `SecurityConfiguration.paranoid()` — `strict()` plus the application-layer content detection

`paranoid()` differs from `strict()` in exactly two settings: it seeds `blockedPathPatterns` from
`SecurityDefaults.SENSITIVE_PATH_PATTERNS` and `blockedParameterNames` from
`SecurityDefaults.SUSPICIOUS_PARAMETER_NAMES`. Those literals are filesystem paths, configuration
filenames and generic parameter names, so the preset rejects a request whose path carries a
matching `/`-delimited segment (for example `/config/etc/settings`) and a request whose parameter
name is exactly `file`, `path` or `url` — all legitimate vocabulary in many REST APIs. Choose it
where URL paths and parameters really do reach a filesystem; otherwise seed a narrower list of your
own on another base preset. Both block-lists are orthogonal to the strictness predicate, so
`paranoid().isStrict()` is `true`.

Build a custom configuration with `SecurityConfiguration.builder()`.

== Length limits

Enforced by `LengthValidationStage`, which runs first in each of the five value pipelines to
prevent DoS. (The exception is `ContentTypeValidationPipeline`, which is a single
`AllowBlockListStage` and has no length stage.)

[cols="3,1,1,1,1", options="header"]
|===
| Setting | default | strict | paranoid | lenient
| `maxPathLength`          | 4096 | 1024 | 1024 | 8192
| `maxParameterNameLength` | 128  | 64   | 64   | 256
| `maxParameterValueLength`| 2048 | 1024 | 1024 | 8192
| `maxHeaderNameLength`    | 128  | 64   | 64   | 256
| `maxHeaderValueLength`   | 2048 | 1024 | 1024 | 8192
| `maxCookieNameLength`    | 128  | 64   | 64   | 256
| `maxCookieValueLength`   | 2048 | 1024 | 1024 | 8192
| `maxBodySize` (bytes)    | 5 MB | 1 MB | 1 MB | 10 MB
|===

== Encoding and character policy

[cols="3,1,1,1,1,3", options="header"]
|===
| Setting | default | strict | paranoid | lenient | Enforced by
| `allowDoubleEncoding`     | false | false | false | true  | `DecodingStage`
| `allowNullBytes`          | false | false | false | false | `CharacterValidationStage`, `DecodingStage`
| `allowControlCharacters`  | false | false | false | true  | `CharacterValidationStage`, `DecodingStage`
| `allowExtendedAscii`      | true  | false | false | true  | `CharacterValidationStage`
| `normalizeUnicode`        | true  | true  | true  | false | `DecodingStage`
|===

`normalizeUnicode` follows the OWASP _canonicalize-then-validate_ model: input is normalized and
the canonical form flows to downstream stages (normalize-and-continue). It is rejected only when a
fold introduces a structurally significant separator (`/ \ . : ? # %`) — e.g. a fullwidth solidus
`U+FF0F` folding to `/`. Benign compatibility folds of legitimate international text are preserved.
Paths use NFKC; parameter values use the lossless NFC form. NFKC is not confusable/homograph
defense (that is a UTS #39 capability).

`DecodingStage` selects its decoder by validation type: URL path decoding follows RFC 3986 and
preserves a literal `+`, while parameter and body decoding apply form
(`application/x-www-form-urlencoded`) semantics, in which `+` decodes to a space. This is
`DecodingStage`'s own per-type decoder contract, not a statement about wiring: no `BODY` pipeline
exists (`PipelineFactory.createPipeline` rejects `ValidationType.BODY`), so the body branch is
never reached today. `DecodingStage` runs only in the URL path and URL parameter (name and value)
pipelines - the header and content-type pipelines omit it entirely, so none of the decoding rules
above apply to header or content-type validation.

== Pattern matching policy

Enforced by `PatternMatchingStage`.

`PatternMatchingStage` runs in the URL path and URL parameter (name and value) pipelines only, so
`caseSensitiveComparison` and `failOnSuspiciousPatterns` have no effect on header or content-type
validation.

[cols="3,1,1,1,1", options="header"]
|===
| Setting | default | strict | paranoid | lenient
| `caseSensitiveComparison`  | false | false | false | false
| `failOnSuspiciousPatterns` | false | true  | true  | false
|===

=== What `failOnSuspiciousPatterns` governs

`failOnSuspiciousPatterns` governs exactly one check: whether a URL path or parameter value that
*starts with* one of `SecurityDefaults.PROTOCOL_HANDLER_SCHEMES` (`javascript:`, `vbscript:`,
`data:`, `file:`) is rejected. That check is structural — a path component that *is* a
scheme-bearing URI is not a valid path component, independent of what the receiving application
does with it — which is why it stays enforced in `strict()`. With the flag `false`, a scheme match
is permitted silently: the stage does not log, count or otherwise report it.

The application-layer content judgement is *not* governed by this flag. Sensitive filesystem paths,
sensitive filenames and suspicious parameter names are decidable only with knowledge of the sink
the value flows into, which the library does not have, so they live on the two configurable
block-lists below and are enforced only where a caller has seeded them. See
link:../adr/0015-A_pattern_literal_enforced_by_a_named_preset_must_be_decidable_from_the_HTTP_component_alone.adoc[ADR-0015]
for the admission rule this split follows.

Path-traversal detection (`../` and its encoded variants) is unconditional in every preset and is
governed by no flag at all.

== Attack-pattern block lists

Two configurable block lists (default empty) carry the application-layer content judgement. Each is
enforced by `PatternMatchingStage` whenever *that list* is non-empty — neither is gated on
`failOnSuspiciousPatterns`, mirroring the header-name and content-type block lists, which are
likewise gated only on their own contents.

[cols="3,3,2,3", options="header"]
|===
| Setting | default (defaults/strict/lenient) | paranoid | Matcher semantics
| `blockedPathPatterns`
| empty (block-none)
| `SENSITIVE_PATH_PATTERNS`
| Whole `/`-delimited path segment, compared against `URL_PATH` and `PARAMETER_VALUE`. The
  pattern's leading and trailing `/` are stripped, so `/etc/` matches an `etc` segment. A pattern
  containing a backslash is matched as a substring instead — its own delimiters already anchor it,
  and a decoded backslash cannot occur in a legitimate URL path.

| `blockedParameterNames`
| empty (block-none)
| `SUSPICIOUS_PARAMETER_NAMES`
| Exact string equality against `PARAMETER_NAME`.
|===

Both lists follow `caseSensitiveComparison`: with the default `false`, list and input are lowercased
before comparison, so an all-lowercase list still matches mixed-case input.

The matchers are deliberately precise rather than substring-based. `blockedPathPatterns` matching a
whole segment is what keeps `/documents/document.envelope` accepted under a list containing `.env`,
and the scheme check anchoring on the *whole* value — not on each segment — is what keeps
`/v1/data:export` and `/api/profile:read` accepted.

The scheme anchor is applied to the value a URL *parser* would read: ASCII TAB, CR and LF are
removed from anywhere in the value and leading C0 controls and spaces are skipped before the
comparison, because a parser does the same before it determines the scheme. Without that step a
parameter value of `%09javascript%3Aalert(1)` would clear the anchor while still being a
`javascript:` URL to every browser — CR, LF and TAB are legitimate form-data content in a
`PARAMETER_VALUE` and therefore reach this check intact. The normalisation positions the anchor
only; the value that flows on to the caller is never the stripped view.

=== Why the two lists are separate

They apply different matching semantics to different HTTP components: a path pattern matches a
whole path segment of a `URL_PATH` or `PARAMETER_VALUE`, while a parameter name matches a
`PARAMETER_NAME` by exact equality. A single combined list would have to pick one semantics and
would then misapply it to the other component — seeding it with the parameter name `file` would
also reject every path carrying a `file` segment.

[source,java]
----
// Reproduce the paranoid() detection on any base preset
SecurityConfiguration config = SecurityConfiguration.builder()
    .blockedPathPatterns(SecurityDefaults.SENSITIVE_PATH_PATTERNS)
    .blockedParameterNames(SecurityDefaults.SUSPICIOUS_PARAMETER_NAMES)
    .build();

// Or seed only what matches your application's sink
SecurityConfiguration narrow = SecurityConfiguration.builder()
    .blockedPathPatterns(Set.of("/etc/", ".env"))
    .build();
----

The seeding constants in `SecurityDefaults` — `SENSITIVE_PATH_PATTERNS` (the six Unix filesystem
paths, five sensitive filenames and four backslash-delimited Windows filesystem paths) and
`SUSPICIOUS_PARAMETER_NAMES` (eight generic names) — are
reference values, exactly like the header and content-type classification constants below.
`PROTOCOL_HANDLER_SCHEMES` is *not* a seeding constant: it backs the structural scheme check
directly and is not caller-configurable.

== Collection count limits

Request-level limits enforced by `RequestCollectionValidator` (a single-value pipeline cannot
count a collection). Defend against resource-exhaustion / hash-collision DoS.

[cols="3,1,1,1,1", options="header"]
|===
| Setting | default | strict | paranoid | lenient
| `maxParameterCount` | 100 | 20 | 20 | 500
| `maxHeaderCount`    | 50  | 20 | 20 | 100
| `maxCookieCount`    | 20  | 10 | 10 | 50
|===

[source,java]
----
RequestCollectionValidator validator = new RequestCollectionValidator(config, counter);
validator.validateParameters(request.getParameterMap());
validator.validateHeaders(request.getHeaderMap());
validator.validateCookies(request.getCookies());
----

== Cookie attribute requirements

Opt-in (default `false`) requirements enforced by `CookiePrefixValidationStage.validateCookie(Cookie)`.
Meaningful only for attribute-bearing (Set-Cookie) cookies, not request `Cookie`-header
`name=value` pairs.

[cols="3,1,1,1,1", options="header"]
|===
| Setting | default | strict | paranoid | lenient
| `requireSecureCookies`   | false | false | false | false
| `requireHttpOnlyCookies` | false | false | false | false
|===

== Header-name and content-type allow/block lists

Case-insensitive allow/block lists (default empty). Block-list takes precedence; an empty
allow-list means allow-all. Enforced by `AllowBlockListStage`.

The empty *value* is a separate matter from the empty *list*: an empty value is evaluated against
the lists like any other value and is not exempt. A non-empty `allowedContentTypes` or
`allowedHeaderNames` therefore rejects the empty string, and a block-list containing the empty
string rejects it too.

[cols="3,1,3", options="header"]
|===
| Setting | default (all presets) | Enforced by
| `allowedHeaderNames`   | empty (allow-all) | header-name pipeline (`HTTPHeaderValidationPipeline`, `HEADER_NAME`)
| `blockedHeaderNames`   | empty (block-none)| header-name pipeline (`HTTPHeaderValidationPipeline`, `HEADER_NAME`)
| `allowedContentTypes`  | empty (allow-all) | `ContentTypeValidationPipeline` / `PipelineFactory.createContentTypePipeline`
| `blockedContentTypes`  | empty (block-none)| `ContentTypeValidationPipeline` / `PipelineFactory.createContentTypePipeline`
|===

[source,java]
----
SecurityConfiguration config = SecurityConfiguration.builder()
    .blockedHeaderNames(Set.of("X-Debug", "X-Test"))
    .allowedContentTypes(Set.of("application/json"))
    .build();
----

The classification constants in `SecurityDefaults` (`DANGEROUS_HEADER_NAMES`,
`DANGEROUS_CONTENT_TYPES`, `SAFE_CONTENT_TYPES`, …) are reference values you may feed into these
lists.
